## 3. 被钉死的「现状怪癖」（S5/S6/S7 必须复刻或显式登记偏差）

以下行为看似反直觉，characterization 一律如实锁定，**不在 M1 顺手修正**：

1. 过滤 `contains/startsWith/endsWith` 传**空字面量**恒真（任意串包含空子串）。
2. `eq/neq` 一侧无法 `toNumber` 时回退为**文本严格相等**；布尔按 1/0 参与数值比较；
   数字单元格 vs 千分位字面量 `"1,234"` 因 `Number("1,234")=NaN` 而不相等。
3. 日期 `gt/lt/gte/lte/eq` 走 `Date.parse` 时间戳；但日期 `is` 走文本严格相等（不做时间戳归一）。
4. checkbox 文本 `"maybe"` 既不 checked 也不 unchecked。
5. 多选数组 `contains` 是「任一元素子串命中」，跨元素拼接串不命中；
   `isAnyOf/isNoneOf` 对数组元素做大小写不敏感**精确**相等；空列表字面量 → anyOf=false、noneOf=true。
6. 匹配字段（valueType=field）下，`isAnyOf` 对数组目标用「整串参照文本」比对单元素（多数情况 false）。
7. 分组：singleSelect/multiSelect 的桶 `label` 是**存储原文 optionId**（不是选项 name），
   `color` 因按 `option.name` 匹配 optionId 失败而恒为 `null`；checkbox 桶 label 固定中文、
   color 固定硬编码 `#1D9E75/#888780`；空白桶 key=`__empty__`、label=`(空白)` 永远最后；
   多选一条记录进多个桶；空数组与 null 同进空白桶且 recordIds 去重。
8. `queryRecords`：`total`=过滤前全表活记录数，`filteredTotal`=过滤+搜索后/分页前；
   默认排序在 DB 层 `(createdAt ASC, id ASC)`；内存 sort 空值恒后（asc/desc 皆然）；
   分页是内存 `slice(offset, offset+limit)`，**只切 records**，groups/aggregations/total 仍是全量；
   默认 limit=200，路由层 clamp 到 1000，非法 limit/offset 回退默认。
9. `collapsedGroupKeys` 非空时分组仍照常计算（当前不折叠/不过滤）。
10. `assertUnique` 用 `stored[f.id] === v` **严格相等**：数字 `123` 与字符串 `"123"` 不冲突；
    `undefined/null/""` 全跳过（多空值不冲突）；只查 `deletedAt:null`；冲突文案固定
    `字段「<name>」要求唯一，该值已存在`（409）。

## 5. 大表（1 万 / 10 万）改造前性能基线 —— 方法与占位

M1 plan S0 要求记录 1 万 / 10 万档「改造前延迟与查询条数」，作为 A/B 对照的 A。
数据生成器与压测脚手架在 **S9**（`scripts/bench/*`）才落地，S0 阶段尚不存在可复现的
大数据集与受控 harness，此处**不伪造数字**，先固定方法，待 S9 产出后回填本节：

- 数据集（S9 生成器，固定随机种子）：
  - 单表 `n=10_000` 与 `n=100_000` 两档；字段构成 = 文本主字段 + number + date +
    checkbox + singleSelect + multiSelect + 一个 mm links（关联到同库另一张 1/10 规模表）。
  - 每档另生成 10% 软删行，验证活记录计数与索引路径。
- 度量方法（S10 `scripts/bench/run-gate.mjs` 同口径）：
  - 冷启动后顺序 50 次 `GET /records?tableId=…&limit=200`（首页）与深翻页 `offset≈n/2`，
    取 P50/P95 端到端毫秒（服务端计时，非 localhost 网络噪声时用 `performance` 中间件）。
  - 查询条数：对 better-sqlite3 / Prisma 加临时查询计数包装（与 S0
    `hydration.batch-parity.test.ts` 同款 deps 计数思路），记录每请求 SQL/取数调用数。
  - 写并发：20 并发 PATCH，统计成功率 / SQLITE_BUSY(5) 次数（S1 写队列 on/off 对照）。
- 现状旁证（非 M1 受控 harness，仅历史参照）：`docs/benchmark-api.md`（2026-09-07，
  Stress_2000 表）记录 2000 行下 `GET /records?limit=500` 平均 13.9ms、
  并发批量写(batch=20) 失败率约 50%。
