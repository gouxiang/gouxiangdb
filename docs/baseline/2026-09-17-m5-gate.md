## 1. EXPLAIN 证据：三路召回收敛先于产出（§4.5 EXPLAIN 铁律）

夹具：真迁移主库 + 真 search.db（加载 vec0 v0.1.9），`runRecall(..., { explain:true })` 采集计划
（`query-s11-gate.test.ts` S11-A 三例）。以下为实测计划文本（`temp_scope_<hex>` 为唯一后缀临时表名，
README 处统一掩码为 `<hex>`）：

### 1.1 FTS 路（码元≥3，trigram MATCH）

```
SCAN fts_chunks VIRTUAL TABLE INDEX 0:M5
SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
CORRELATED SCALAR SUBQUERY 2
SCAN g0
CORRELATED SCALAR SUBQUERY 3
SCAN g
SEARCH s USING COVERING INDEX sqlite_autoindex_temp_scope_<hex>_1 (nodeId=?)
CORRELATED SCALAR SUBQUERY 1
SCAN f VIRTUAL TABLE INDEX 0:=
USE TEMP B-TREE FOR ORDER BY
```

### 1.2 LIKE 路（码元<3，参数化 title/body 子串）

```
SCAN f VIRTUAL TABLE INDEX 0:
SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
CORRELATED SCALAR SUBQUERY 1
SCAN g0
CORRELATED SCALAR SUBQUERY 2
SCAN g
SEARCH s USING COVERING INDEX sqlite_autoindex_temp_scope_<hex>_1 (nodeId=?)
```

### 1.3 vec 路（KNN，rowid IN 白名单子查询）

```
SCAN vec_chunks VIRTUAL TABLE INDEX 0:3{___}___[___&Ag_
LIST SUBQUERY 5
SCAN c
CORRELATED SCALAR SUBQUERY 2
SCAN g0
CORRELATED SCALAR SUBQUERY 3
SCAN g
SEARCH s USING COVERING INDEX sqlite_autoindex_temp_scope_<hex>_1 (nodeId=?)
SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
…
CORRELATED SCALAR SUBQUERY 1
SCAN f VIRTUAL TABLE INDEX 0:=
USE TEMP B-TREE FOR ORDER BY
```

### 1.4 判读

- 三路都出现 `temp_scope_<hex>` 的**COVERING INDEX 搜索**（`SEARCH s USING COVERING INDEX … (nodeId=?)`）：
  表级权限收敛（scope）以临时表的覆盖索引参与计划，发生在结果产出之前。
- FTS/LIKE 计划中的 `CORRELATED SCALAR SUBQUERY`（`SCAN g0` / `SCAN g`）即 `temp_field_grant`
  三分支 allowed 谓词（identity 恒可见 / 无 mask 表放行 / 有 mask 表命中白名单）——字段级收敛同在先。
- vec 路的白名单 `rowid IN (SELECT rid FROM allowed)` 下推为 `LIST SUBQUERY`，其内即 `temp_scope`
  覆盖索引搜索；`SCAN vec_chunks VIRTUAL TABLE`（vec0 本就 SCAN，无 ANN）配上该子查询约束
  = 收敛发生在 KNN 扫描约束中，**非「全量 KNN 后应用层过滤」**（§4.5 步骤 4c 红线）。
- 对应断言：`query-s11-gate.test.ts` 三例（FTS→`temp_scope_`+`fts_chunks`；LIKE→`temp_scope_`+
  `CORRELATED SCALAR SUBQUERY`；vec→`vec_chunks`+`LIST SUBQUERY`+`temp_scope_`）。

## 2. SQL 计数常量化（与节点数/主体数解耦）

口径：对 `SearchDbLike`（`store.db`）做最小计数包装，统计一次 `runRecall` 内所有经 `prepare`/`exec`
的语句（`query-s11-gate.test.ts` S11-B；包装先例同 M4 `query-count.test.ts` 的 Proxy 计数）。

| 规模 | scope 节点 | grant 行 | 召回语句数 | 说明 |
|---|---|---|---|---|
| 基础（同批） | 1 | 0 | **6** | CREATE TEMP×2 + INSERT scope×1 + 召回×1 + DROP TEMP×2 |
| 同批 | 450 | 0 | **6** | 与 1 节点**完全一致**（语句种类逐条相同）-> 与节点数解耦 |
| 超一批 | 500 | 0 | **7** | 仅多一条 INSERT（⌈500/499⌉=2 批） |
| 超两批 | 1000 | 0 | **8** | 仅多一条 INSERT（⌈1000/499⌉=3 批）；非 INSERT 语句恒 5 条 |
| 带 mask | 3 | 450 | **7** | 仅多一条 `temp_field_grant` 批量 INSERT；与 mask 字段数解耦（3 行同 7 条） |

结论：

- **权限收敛相关语句与节点数/主体数解耦（常量级）**：建表、召回、清理恒为固定条数；唯一随规模变化的是
  `temp_scope`/`temp_field_grant` 的**批量 INSERT**，且按每 499 行一批亚线性增长（SQLite 999 变量上限内）。
  召回 SQL 本身恒为 1 条（不与节点数/主体数成比例）。
- **主体侧 SQL 不在本层**：主体/角色/部门 → scope 的求值在 M4（已在 M4-S10 门与 `query-count.test.ts`
  定数化）；`runRecall` 只消费已解析的 `scope.nodeIds`，故本片只对**召回侧**做常量断言，不重复 M4 口径。

对应断言：`query-s11-gate.test.ts` S11-B 四例（同批 1 vs 450 语句数+形态集一致；grant 0 vs 450 仅 +1；
500 vs 1000 仅 +1 且非 INSERT 恒 5；召回语句恒 1）。

> 复核：以上为**小规模**下界证据。S13 将给规模曲线（1k/1万/10万 chunk 的 KNN 扫描/存储/RSS 与
> EXPLAIN「无先全量召回」），本片不声称完成 S13。

## 3. RRF 标题 boost 标定（§4.5 步骤 5）

### 3.1 常量与标尺

依据 §4.5 步骤 5「标题精确等于 q / 前缀命中加固定 boost」。默认 `k=60` 时单路 rank=1 的 RRF 权重
为 `1/(60+1) ≈ 0.016393`——取其为标尺：

| 常量（`rrf.ts` 导出） | 取值 | 与 1/(k+1) 的关系 |
|---|---|---|
| `TITLE_EXACT_BOOST`（标题精确等于 q） | `0.016` | ≈0.98 个 rank-1 单位，**严格小于一整个单位** |
| `TITLE_PREFIX_BOOST`（标题以 q 为前缀） | `0.008` | exact 的一半 |

语义：实体**任一命中 chunk 标题**（record identity=记录 id、record field=字段名、doc/canvas=标题(+章节路径)）
等于查询（trim + 大小写不敏感）得 exact 加成、以其为前缀得 prefix 加成；**每实体至多加一次**（跨路取最大）。
仅当 `reciprocalRankFusion(..., { titleQuery })` 给出且非空时加成；缺省/空则零加成，计分与历史逐位一致。

### 3.2 为什么是这个值（两条硬约束）

1. **单调**：`exact > prefix > 无加成`。因 `0.016 > 0.008 > 0`，且均计入正分，排序可解释。
2. **有界/不位移**：exact 严格小于**一整个 rank-1 单位**，故
   `单路 rank-1 标题精确命中 = 1/61 + 0.016 ≈ 0.0324` **<** `两路 rank-1 正文命中 = 2/61 ≈ 0.0328`
   —— 标题加成**不会把多路正文强命中挤出**（「不把明显不相关的向量命中顶掉」的反向保证：也不越级
   压过多路强命中）。同时 exact 加成足以把强名次的标题命中拉到纯正文命中（单路 rank1 = 0.0164）之上。

### 3.3 小样标定表（确定性，`rrf-title-boost.test.ts`）

查询 q=「季度报告」，样本（route, entity, rank, title）：

| 实体 | 路 | rank | 标题 | 加成 | score |
|---|---|---|---|---|---|
| doc:bodyStrong | fts+vec | 1,1 | 无关文档标题 | 0 | 2/61 ≈ 0.032787 |
| doc:exactWeak | fts | 6 | 季度报告 | exact 0.016 | 1/66+0.016 ≈ 0.031152 |
| doc:prefixA | fts | 2 | 季度报告 / 背景 | prefix 0.008 | 1/62+0.008 ≈ 0.024129 |
| record:veconly | vec | 1 | rec_9（不匹配） | 0 | 1/61 ≈ 0.016393 |

标定结论（已逐条断言）：

- 排序 = `bodyStrong > exactWeak > prefixA > veconly`；
- 样本内非位移：两路正文强命中（0.0328）> 单路精确标题命中（0.0312）——boost 有界、不越级；
- 标题命中跨名次可压过更靠前的无标题命中（exactWeak rank6 > veconly rank1）；
- 不相关的纯向量命中（标题=记录 id）不被顶到标题命中之前。

### 3.4 接线与可观测（`query.ts`）

- `routeToHits` 透传 `chunk.title`；`reciprocalRankFusion(..., { topN: limit, titleQuery: plan.query })`
  （`plan.query` 为 trim 后原始查询词）。
- `FusedCandidate` 增 `titleBoost` 字段（已计入 `score`；便于测试/诊断，不改变响应结构）。
- 端到端接线断言（`query-title-boost.test.ts`，真 search.db + 真 `executeUnifiedSearch`）：
  标题精确命中实体 `score > 1/61` 且排首位；仅正文命中实体 `score ≤ 1/61`；无标题命中时全部
  `score ≤ 1/61`（默认零行为变化）。fts 与 like 两形态各一例。

### 3.5 与冻结契约/ shadow 的关系

- **旧 `/api/search`（S0 golden）零 diff**：boost 只在新链 `rrf.ts`（旧链不引用该模块）；golden 快照
  字节不变（`git diff` 空，门测试 5/5 通过）。
- **新链响应结构不变**：`mode`（按实际执行路）/`degraded`/`policyVersion`/`items` 字段与语义不变，
  boost 只影响 `score` 值与排序；无 boost 命中时逐位一致。
- **shadow（`compareSearchShadow`）影响**：boost 只改新链候选的**分值/顺序**（topN 截断后可能改变纳入集），
  不新增/不删除候选的计算路径。约定「可比集」为**两链都用 FTS/LIKE** 的交集；在该集上 RRF 与旧链
  （records→docs 物理序，ADR-0005 有界预览）顺序本就不保证相同。经全量回归核验：
  - 现存 shadow 断言（`queryShadow.test.ts` 纯比较、`query-v1-route.test.ts` HTTP 壳）**全绿**；
  - `drift=0` 的 HTTP 例是单实体可比（顺序无关，boost 不改变其 drift）；
  - 无任何测试断言「多实体可比集 strict 下 drift=0」。故 boost 对本片**未引入 strict 失败**，
    无需放宽闸门、无需在可比集口径排除 boost。
