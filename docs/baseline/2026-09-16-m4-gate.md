## 1. 规模门实测（500 用户 / 6 层部门 / 万节点 / 约 3000 策略）

夹具复用 S4 `scopeScaleHarness.ts:seedScale`（固定 seed 20260916 的 mulberry32，跨次可复现），
不重造：500 用户、31 部门（1 根 + 5 层各 6）、人均约 2 部门、10000 nav 节点
（40 base + 400 table + 9560 doc，约 2% inheritAncestors=0）、3000 策略
（1000 user + 50 带 fieldMask 的 table user + 1000 sr_read + 500 sr_ru + 450 dept）。

| 项 | 实测 | 门要求 | 结论 |
|---|---|---|---|
| scope 客体 SQL（非 owner） | 恰 4 条：authPolicy.findMany + navNode.findMany + creator UNION ALL($queryRawUnsafe) + workspace.findUnique | <=4 | 过 |
| scope 客体 SQL（owner） | 恰 3 条（跳过 creator UNION） | <=4 | 过 |
| decide 客体 SQL（冷，每请求独立链缓存） | 恰 3 条：navNode.findFirst + navNode.findMany(path IN 一次取全链) + authPolicy.findMany；其后 creator 兜底至多 1 次实体点查（adapter 进程内缓存命中则 0） | 定数，与节点总量/部门深度无关 | 过 |
| decide 客体 SQL（同版本链缓存命中） | 仅 authPolicy.findMany 1 条，无节点往返 | <=3 | 过 |
| scope <-> decide 零分叉 | 12 抽样用户 x 500 等距抽样节点 x r/u 两动作 = 12000 次布尔比较，0 差异 | 0 | 过 |
| policyVersion 读侧 bump | resolveSubject + 63 次 decide + 2 次 scope 前后 workspaces.policyVersion 不变；scope 全程无 workspace.update | 仅写事务 bump | 过 |

### 1.1 P95 时延（本机测试机，机器相关绝对值）

| 路径 | n | P50 | P95 | MAX | 团队线 |
|---|---|---|---|---|---|
| decide 冷决策（独立链缓存 + 真 createdBy 点查，12 用户 x 21 抽样节点） | 252 | 0.32-0.35ms | **0.36-0.41ms** | 0.41-0.79ms | p95<500ms |
| scope 批量可见集（万节点全量内存判定，n=21） | 21 | 35.8-37.8ms | **41.8-44.0ms** | 47.6-53.0ms | p95<500ms |

- 区间为 2026-09-16 同机两次门运行（冷/暖缓存差异），均远低于 500ms 团队线；
  CI 断言留 1000ms 宽松上界防机器波动假阴，绝对值以本表为准
  （与 S4 baseline 2026-09-15 记录的 scope P95=43.7ms 同量级，无回退）。
- decide 亚毫秒说明三源 OR + cutoff 链收集在 3000 策略规模下无压力；scope 的 35-44ms
  几乎全部是万节点全量拉取 + 逐节点内存判定（M5 检索召回的既有预算口径），不是单条 SQL 慢。

## 2. policyVersion bump 频率（仅写事务）

- bump 点全仓仅两处，均在 `withWriteTx` 内：
  - `policyAdminTx.ts` PUT policies 整单成功后 `workspace.update policyVersion+1`（整单拒不 bump，
    policies-api「一合法一非法整单拒」用例锁定）；
  - `inheritance.ts` PATCH 继承开关（实际翻转才 bump；幂等重放不 bump，s7-inheritance 锁定）。
- 读链路（resolveSubject / decide / resolveVisibleNodeIds / GET policies / GET effective /
  GET breadcrumb）只读 `workspace.findUnique` 取版本随响应回传，**零 update**，S10 用例显式断言。
- 三源即时性（AC-M4-1）不依赖版本等待：移除 role_assignment / 部门调岗 / 删直授后同一 JWT
  下次请求即生效，见 `s10-ac-sources.test.ts`。

## 3. 三层就绪门矩阵（S10 末态，纯函数实测）

三个门在 `configAuthz.ts` 独立存在，本切片**未改任何默认**：

| 常量 | S10 末值 | 真实生产接线 |
|---|---|---|
| `AUTHZ_ENFORCE_READY`（七守节点守卫总门） | **false** | 无：七守仅挂 shadow 对拍，无「以引擎为准」分支 |
| `FIELD_MASK_ENFORCE_READY`（S6 字段掩码五出口） | true | maskGate.ts：records 列表/详情/写键/CSV |
| `NAV_PRUNE_ENFORCE_READY`（S7 tree/menu 剪枝 + 面包屑） | true | breadcrumb.ts / routes/v1/workspace.ts |

env `GX_AUTHZ_ENGINE` 三态下各生效面（on 经总门降级规则）：

| env | effectiveAuthzMode | shadow 对拍 | fieldMask enforce | navPrune enforce |
|---|---|---|---|---|
| off（默认/未知/空） | off | 关（零引擎 SQL） | 关 | 关 |
| shadow | shadow | **开** | 关 | 关 |
| on | **shadow（总门 false 降级 + 一次 warn）** | **开** | **开**（读原始 env，不经降级） | **开**（读原始 env，不经降级） |

矩阵含义（翻转演练据此设计）：

1. 生产「切 on」要真正以引擎决策为准，缺两块：七守 enforce 生产接线 + `AUTHZ_ENFORCE_READY`
   翻 true。两者都不在本切片（S10 产出列=只增测试/文档；派工禁止改 configAuthz 默认）。
2. 总门 false 期间 env=on 的真实效果 = 「shadow 对拍 + 字段掩码 + 树剪枝」三件套同时生效，
   但旧七守对**资源可达性**仍以旧三表为准。这是有意的安全姿态：剪枝/掩码只减不增，
   不会放行任何被旧守卫拒绝的请求。
3. v1 新端点（policies/effective/visible-scope/inheritance）不经三态 flag，任何模式下都
   直接走引擎（M5/M6 同纪律：新通道从第一天只认引擎）。

## 4. 翻转演练（off -> shadow -> on 语义 -> 反向 shadow -> off）

测试 `s10-flip-drill.test.ts`（5 例，真迁移临时库 + 真 app/真 JWT，零生产码）。
因七守无 enforce 生产分支（§3），演练严格区分「真实 HTTP 行为」与「测试内以引擎为权威的 on 语义」：

| 步骤 | env | 实测结果 |
|---|---|---|
| 1/5 off 基线 | off | 七族读探针 owner 全 200、stranger 全 403/404；drift compared=0（最末用例另证 authPolicy 零查询） |
| 2/5 shadow | shadow | 同批探针状态码与 off 快照逐值相等；overDeny=overAllow=errors=0、compared>0 |
| 3/5 on 语义 | on | READY=false 锁定、effectiveAuthzMode(on)=shadow；HTTP 结果与 off 快照相等（**无请求因 env=on 被引擎真拒绝**）；测试内以 engineDecideResource 为权威，七守（view/edit/comment/schema/share/kb/doc）x 四主体 = **28 格布尔与旧守卫期望全等** |
| 4/5 反向 shadow | on(降级) | 测试内独立 DriftRegistry 对 (旧 HTTP, 引擎) 分类：28 格双零；人工插越权行 -> OVERALLOW 分类正确且 HTTP 仍 403；删 editor 投影 -> OVERDENY 分类正确且 HTTP 仍 200；reconcile 还原 |
| 5/5 回 off | shadow -> off | 状态码逐值恢复；off 下 authPolicy 零查询、compared=0；A-5 角色授予行保留（旧表零行、stranger 旧守 403），引擎 decide 仍 allow=重开即恢复 |

- 用例数：5（每例内含 4 主体 x 4-7 守的多点断言）。on 语义对拍格数 28（步骤 3）+ 28（步骤 4 反向）。
- 全程不改任何生产码、不翻 `AUTHZ_ENFORCE_READY`（用例内 `expect(AUTHZ_ENFORCE_READY).toBe(false)` 锁死）；
  env 仅在用例间显式置位/还原。
- 含义：现有构建在 env=on 下的真实效果是「shadow 对拍 + 字段掩码 + 树剪枝」三件套，
  **资源可达性仍由旧七守裁决**；一旦未来 enforce 接线切片落地，步骤 3 的 28 格等价证明
  与步骤 4 反向计数即为「接线正确性应保持的基线」。这是 M4 出口 shadow 可发布姿态的证据，
  不是「七守已 enforce」的声明。
