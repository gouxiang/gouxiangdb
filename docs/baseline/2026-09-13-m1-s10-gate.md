## 4. 根因分层（两层独立问题）

1. **物理索引层：健康。** 50 万行带过滤命中 0.4–12ms、无 SCAN，索引（`rfi_table_field_num/text`、`rfi_table_record`、`records_table_live_created_id`）齐备且被规划器选中。这一层不是瓶颈，迁 PG 无收益。
2. **应用 hydration 层：瓶颈所在。** 宽表 mm 关联是 u^4 幂分布随机图（少量早期 main 为超大 hub）。
   - pre-fix：`hydrateBatch` BFS 沿"该表所有 link 字段"最多 8 跳、无总量上限，连通分量近整表。实测 10k 一个首页（100 根）记录缓存被灌到 **12,220 条**（depth0 +1420、depth1 +7122、depth2 +2349…），随整表超线性（300 行 41ms→10k 1.4s→100k 45s，约 N^1.5–1.7）。
   - post-fix：深度降到 3、总量预算夹 [400,2000]、预算外走 cache-miss，串行墙钟大幅下降且逐值不变；但①预算闸只约束对端记录载入（`getRecordsByIds`），`expandLevel` 的 `loadGroups` 在预算检查**之前**对该表**所有** link 字段无差别批量拉 link_rows，包括**没有任何计算字段引用**的关系；②计算字段 lookup/rollup/count 在取值阶段对偏态 hub 仍物化其全部关联行；③预算外兜底是单条 N+1（C=8 下 270+ 往返经同步驱动串行化）。
   - 扇出实测（首页 createdAt 最老 100 根，恰含 u^4 超级 hub）：
     - `children`（mm，被 childTitle/childSum/childCount/firstChild 四个计算字段引用）：生成器限定每 main 0..6 条，三档恒定 288–309 行、max 6/根——**本就有界**。
     - `ownerLink`（hm 一对多，"归属"，**无任何计算字段引用**）：10k 1,272 行/max 424 → 100k 6,998/max 2,259 → 500k **23,337 行/max 7,523**。post-fix 的 35s 主要在为这条无引用关系做无界 link 行物化与后续 peer 处理。
   - 三者都是**应用层取数/物化形状**问题：PostgreSQL 不会减少应用发出的查询数，也不会让"把一个 hub 的全部关联行读进 JS 算 sum/count"或"展开无字段引用的关系"变快。

## 6. ADR-0008 客观判定

计划 §S10 触发需**同时**满足：S1/S4/S5/S6/S7 全上线、sidecar drift=0、EXPLAIN 确认命中索引（无全表 SCAN）、计算字段已置灰——在此前提下**物理索引命中场景 100 万行 P95 仍 ≥1.5s（5 轮 ≥3 轮超标）**，或首页 ≥800ms，才判 SQLite 证伪、立项迁 PG；且 fail 也要"先给调索引/调 bound 的二次尝试清单再谈迁库"。

逐条核对：

| 前提 | 本轮事实 |
|---|---|
| S1/S4/S5/S6/S7 上线 | 已上线（flags 灰度，本轮 on/on/on） |
| sidecar drift=0 | S9（commit `ad684d2`）三档端到端写后离线对拍 drift=0；S10 改动均在读路径预取/readyz 探针/生成器，不改 sidecar 同事务写维护逻辑，该结论沿用。S10 大库干净写轮复跑列入残余工作（见 §7） |
| EXPLAIN 命中索引、无 SCAN | 命中场景全部满足（§2，500k 0.4–12ms） |
| 计算字段已按 §2.3 置灰 | **前端 S8 已做交互置灰；但后端列表 hydration 对返回行的计算字段仍实际计算**（见下"残余工作"） |
| 物理命中场景 1M P95 ≥1.5s | 不成立——500k 物理命中仅 0.4–12ms，1M 未在本机跑（规格不足） |

**裁决：不触发 ADR-0008，不立项迁 PostgreSQL。** 理由：被压垮的是应用层计算字段 hydration（关联扇出/N+1），不是 SQLite 的物理索引能力；EXPLAIN 已证明索引路径在 50 万行亚毫秒。迁 PG 不会改变应用取数形状，属"凭感觉迁库"，违反计划客观门。正确动作是先做下列"二次尝试"。

### 迁库前必须先做的二次尝试（按收益排序）

1. **预取按"被引用关系"剪枝**（最高性价比、纯应用层、不改取值）：`expandLevel` 当前对一表所有 links/subtable 字段无差别展开；应只展开"当页计算字段/公式实际依赖"的 link 字段。本例 4 个计算字段只引用有界的 `children`（≤6/根），却被无引用的 `ownerLink` mega-hub（500k 首页 23,337 link 行、单根 7,523）拖垮。剪枝后首页关联物化量从 O(整图偏态) 降到 O(页大小×有界度)。
2. **计算字段聚合下推 SQL**：对确需聚合的关系，rollup(sum)/count/lookup 改为在 `link_rows JOIN record_field_index` 上 `COUNT/SUM/GROUP BY`，不把 hub 全部关联行读进 JS 逐行累加。
3. **loadGroups 纳入预算 + cache-miss 兜底批量化**：link 行批量拉取也受总量预算约束；预算外对每个计算字段按"整页根集合"发批量 IN（而非 270+ 单条），把 post-fix 的高并发 prisma 往返压回与页大小无关的常量。
4. **并发口径分离**：better-sqlite3 同步驱动使 C=8 读在事件循环串行化；分别报告"单轮 P95"与"C=8 P95"，门阈值按生产真实并发（裸机单写多读、读多为短事务）核定，避免把同步驱动排队误记成存储引擎不行。
5. 上述落地后，在**固定 4C8G+SSD 压测机**重跑 50 万 / 100 万 5 轮取 P95 中位数，再据实判定。
