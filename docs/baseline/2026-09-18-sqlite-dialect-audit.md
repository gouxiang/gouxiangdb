## 0. 口径声明（先读这一节）

1. **本仓是 SQLite 单库长期路线，不是跨库兼容项目。**
   `apps/api/prisma/schema.prisma:13` `provider = "sqlite"`；
   `apps/api/prisma/migrations/migration_lock.toml` `provider = "sqlite"`；
   ADR-0002 明确 SQLite。因此本文列举的 SQLite 专有写法，**绝大多数是"自觉使用"而非疏漏**——
   没有 SQLite 的 `PRAGMA journal_mode=WAL`，就没有 M0/S5 的在线备份与读写不互斥；
   没有 FTS5/vec0，就没有 M5 的统一检索。
   本文的目的不是"消灭方言"，而是**把"哪些地方故意绑死在 SQLite 上"变成一张可核查的清单**，
   将来若真要出 PostgreSQL 目标，能一眼知道要改哪几处、每处的替代方案是什么。

2. **两条不同的判据，必须分开看。**
   - 计划 §8.1 的字面要求是「**企业版迁移**无 SQLite 专有写死」——作用域是 `prisma/migrations/` 的 SQL。
   - 清单标题写的是「白名单逐处注释」——要求的是**可核查性**，不是零方言。
   因此本文把「迁移 SQL」与「应用层 SQL/API」分列（§1 与 §2）：
   **§1 直接决定本项过不过，§2 登记但不判定**（理由见 §4）。

3. **人工可控 vs 生成器不可控。**
   - Prisma 生成器自动产出的迁移（含 `PRAGMA defer_foreign_keys/foreign_keys` 样板、`-- CreateTable/-- AlterTable` 标记）：
     人工不可控，逐条加注释会在下次 `prisma migrate dev` 时被冲掉。**只能登记、不能注释。**
   - 手写迁移（`migration.sql` 由人编写、无生成器标记）：人工可控，**凡有方言必须就地注释**。
   - 应用层 `.ts`：人工可控，**凡有方言必须有注释**（本仓实际已普遍做到，见 §2）。

4. **ADR-0001 选型写法与实现不符**这一历史偏差不在本文处理范围；本文只记录实现事实。

### 1.1 【类别：AUTOINCREMENT】SQLite 专有关键字硬写死 —— 全仓唯一 1 处，且现有注释结论错误

| # | 位置 | 片段 | 为什么必须用 | 迁 PG 怎么改 |
|---|---|---|---|---|
| A-1 | `apps/api/prisma/migrations/20260913062000_record_field_index_sidecar/migration.sql:16` | `"id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,` | 给可重建的 EAV 旁路表一个单调自增代理主键；`record_field_index` 是先删后插的派生表，用 `AUTOINCREMENT` 保证 rowid 只增不复用，避免回填/对拍期间旧游标误指到新行 | 改 `"id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`（或 `BIGSERIAL`）；语义差异：SQLite `AUTOINCREMENT` 保证严格单调不复用，PG identity 只保证唯一不保证不复用，回填口径需复核 |

**注意（本条是本次巡检最实质的问题）**：该文件第 4–5 行现有注释写的是

```
--   1. 刻意【不用】WITHOUT ROWID（SQLite 专有语法），保 ADR-0008 的 PostgreSQL 通道；
--      普通 rowid 表 + AUTOINCREMENT 主键，两库 DDL 均可平移。
```

其中「**两库 DDL 均可平移**」是**错误结论**：`AUTOINCREMENT` 正是 SQLite 专有关键字，PostgreSQL 不支持。
也就是说 A-1 不只是"缺白名单注释"，而是**有一条会误导后来人的错误注释**——比缺注释更糟。
正确写法应为：明确写「`AUTOINCREMENT` 是 SQLite 专有；此处自觉地用，PG 平移时改 identity」。
（本轮只出文档不改码，故此处仅登记，订正建议见 §4。）

## 3. 缺口：本次**没能确认**的地方（如实登记，不猜）

- **G1｜`DATETIME` 类型名在 PostgreSQL 上是否可平移 —— 未确认。**
  迁移里 65 处 `DATETIME` 全部来自 Prisma SQLite provider 的类型映射。PG 是否接受 `DATETIME` 作为 `timestamp` 的别名，
  本次只做了静态检索、**未起 PG 实例实测**。若不接受，则这 65 处是"生成器产出的、PG 上跑不通的 DDL"，
  届时的改法不是逐处注释而是整体重写迁移。**这一条可能让 §1.3 的分类从"约定"升级为"专有"。**

- **G2｜`DEFAULT CURRENT_TIMESTAMP` 与 Prisma DateTime 的 epoch-ms 整数存储口径是否一致 —— 未确认。**
  `apps/api/src/db/rawRead.ts:6` 写「Prisma 把 DateTime 存为 epoch 毫秒【整数】，故游标 createdAt 用 number(ms)」；
  但迁移里 36 处 `DEFAULT CURRENT_TIMESTAMP` 在裸 SQLite 下产出的是 `'YYYY-MM-DD HH:MM:SS'` 文本。
  二者是否在同一列上混存（Prisma 写入整数、迁移默认值写入文本），本次**未实测**。
  旁证：`docs/runbooks/mcp.md:306` 已经让运维用 `typeof(createdAt)` 去"确认全表类型一致"——说明这个风险已被察觉但未被结案。
  **建议单独立项核查，不计入 ⑦-07 的过与不过。**

- **G3｜运行时字符串拼接的 SQL 无法穷举 —— 部分未确认。**
  `apps/api/src/domain/search/queryPlan.ts` 会按关键词/权限运行时拼出 `like.sql` 与 `allowed` 谓词片段，
  再由 `queryRecall.ts` 拼进主查询。本次只静态确认了其中含 `LIKE ... ESCAPE '\'` 与非递归 CTE 两种形态，
  **无法证明所有运行时组合都不产生方言**。已核对的分支见 §2 各条。

- **G4｜测试 harness 内的方言未逐条清点 —— 只给总数，未逐条列。**
  测试码里存在 `PRAGMA foreign_keys=OFF/ON`（`orgHarness.ts:87,100`、`roles-eval.test.ts:44,48`、`last-owner-bypass.test.ts:62,66`）、
  `PRAGMA table_info(...)`、`sqlite_master` 查询、`wal_checkpoint(TRUNCATE)` 等。
  按本次巡检范围（生产码 / 迁移 / scripts）**排除在清单外**，未逐条登记。若将来要"全仓零方言"，这部分是最大的一块。

- **G5｜`scripts/acceptance/*.mjs` 内的方言只列典型。**
  `scripts/acceptance/lib/db.mjs:55,83,100`（`sqlite_master` / `PRAGMA table_info`）、
  `check-bootstrap.mjs:132`（`sqlite_master`）、`ci-quality.sh:104`（`PRAGMA integrity_check`）、
  `rollback-lib.sh:45` 与 `run-upgrade-drill.sh:100`（better-sqlite3 + WAL checkpoint）。
  全仓 `scripts/` 下 `sqlite_master` 2 处、`PRAGMA` 3 处（**按 grep 计数，未逐文件复核**）。
  验收脚本直接连 SQLite 是本仓既定设计（零 ORM、版本无关），**不改变**，仅登记。

- **G6｜`release/` 目录含迁移副本，不入巡检。**
  `release/api/prisma/migrations/...` 下有迁移文件的副本，但 `release/` 已被 `.gitignore:57` 忽略（`git ls-files release` = 0 行），
  是构建机本地产物，**不属版本库内容**，本次不计入。

- **G7｜`INTEGER PRIMARY KEY` 在 init 迁移里的 rowid 别名语义未单独核查。**
  Prisma 生成器对 `Int @id @default(autoincrement())` 会生成 `"id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT`。
  本次 grep 在 init 迁移里**没有**命中 `AUTOINCREMENT`（只有 sidecar 一处），
  说明业务表主键是 TEXT（cuid），无自增整数主键。此结论基于 grep，**未逐个表核对 schema**。

## 4. 该项能否判"过"—— 建议

### 结论：**建议判「有条件过」，条件是先订正 §1.1 那条错误注释；若本轮不改任何文件，则维持「未做」是保守正确的，但理由必须改。**

理由分三层：

**第一层：团队原判"未做"的依据不完整，应当更正。**
checklist 原文写的判定理由是「**没有任何白名单注释/巡检证据文档**」。
本次巡检发现这个前提**不成立**：

- 5 个企业版手写迁移有**迁移级方言纪律声明**（§1.5）；
- 5 处具体写法有**就地白名单注释**（§1.4 的 D-1~D-5）；
- 3 处有**主动规避方言的注释**（§2.8）；
- M2~M6 全部 12 个手写迁移，**SQLite 专有语法硬写死 = 0**。

也就是说，「企业版迁移无 SQLite 专有写死（SPEC:60）」这句判据，**在 M2~M6 范围内是成立的**。
原判"未做"是 spot grep 只看到了 sidecar 的 `AUTOINCREMENT` 和两处生成器 `PRAGMA`、没看到已有注释导致的。

**第二层：但也不能直接判"过"，因为有 1 处真实缺陷。**
唯一一处 SQLite 专有硬写死（§1.1 A-1）落在 M1/S3 的 sidecar 迁移上，而且
**它那条注释的结论是错的**——写着「两库 DDL 均可平移」，实际 `AUTOINCREMENT` 是 SQLite 专有。
这比"没注释"更危险：它会让将来做 PG 平移的人**相信这里不用改**。
既然本项要的是"可核查"，一条会误导核查者的注释，等于该处**反向不合格**。

**第三层：生成器样板与应用层方言的处置建议。**

| 块 | 建议判法 | 理由 |
|---|---|---|
| M2~M6 手写迁移（12 个） | **过** | 零专有写死 + 5 处头部声明 + 5 处就地注释 + 3 处主动规避注释 |
| M1/S3 sidecar `AUTOINCREMENT`（§1.1） | **遗留 1 条，阻塞"全过"** | 有专有硬写死，且现有注释结论错误 |
| 生成器 PRAGMA 样板（§1.2，8 条） | **登记豁免** | 人工不可控，加注释会被下次生成冲掉；且 PG 目标下这些行是整体删除，不是逐条改写 |
| 应用层 PRAGMA / FTS5 / vec0 / json_extract / sqlite_master / better-sqlite3 API（§2） | **移出本项，另立"PG 平移可行性"议题** | §8.1 字面作用域是迁移；且 ADR-0002/0008 已定 SQLite 单库长期路线，这些是路线的组成部分。把它们塞进 ⑦-07 会让这项永远判不了"过"，也会稀释真正该盯的那 1 条 |

### 关于你倾向的判法，我的不同意见

> 你倾向：手写可控部分逐处有白名单注释＝过；生成器样板部分因不可控而豁免，但要登记。

**方向我同意，但直接照此判"过"我不赞成**，两点补充：

1. **"有注释"不等于"注释对"。** 你的判法只看注释的有无，不看注释的真伪。
   §1.1 那条正是"有注释但注释是错的"——照你的判法它会算"已注释"从而判过，
   而它恰恰是全仓唯一一处真实的专有硬写死。建议判法加一条：**注释结论必须与语法事实一致。**

2. **"手写可控"这个边界要按 M2~M6 划，不能按"全仓手写"划。**
   sidecar 迁移也是手写的、也是人工可控的，但它是 M1/S3 的产物、不在 §8.1 的"企业版 M2~M6"范围内。
   我建议明确写：**M2~M6 判过；M1 遗留 1 条单独挂账**，而不是笼统地说"手写部分过"。

### 若要在本轮内把这一项做成"过"，最小动作（我不做，需指派）

只改 1 个文件、1 段注释，**不改任何 SQL 语义、不改码、不改测试**：
把 `20260913062000_record_field_index_sidecar/migration.sql:4-5` 的
「普通 rowid 表 + AUTOINCREMENT 主键，两库 DDL 均可平移」
订正为
「`AUTOINCREMENT` 是 **SQLite 专有**关键字，此处自觉地用（保 rowid 单调不复用，回填/对拍期间旧游标不误指新行）；
**PG 平移时须改 `BIGINT GENERATED BY DEFAULT AS IDENTITY`**，并复核"严格单调不复用"这一语义差异」。

这一步做完，本项即可判「过」（M2~M6 判据成立 + 唯一专有写死处已有正确的白名单注释 + 生成器样板已登记豁免 + 本证据文档已留档）。
