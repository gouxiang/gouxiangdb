## 1. 任务 #84 根因更正：不是连接池打爆，是慢请求积压触发的 keep-alive 竞态

ADR-0008 §5 把 5000/C8 的 2576 次 status=0 定性为"harness 在 C≥8 下把自身 undici 连接层压爆"，并要求先采集 `error.code`。本轮补采集后定位到的机理比"连接池容量不足"更具体：

- 旧读路径对高命中物理查询**全量物化候选 + 逐行相关 EXISTS**，5000 行带 viewId 场景单请求 7–20s；better-sqlite3 是**同步 native 驱动**，整段查询阻塞 Node 事件循环，C=8 后续请求在单事件循环上排队。
- 排队请求复用的 keep-alive 连接在等待期间空闲超过 Node server `keepAliveTimeout`（默认 5s）被服务端半关闭；undici 复用该死连接发请求即 **ECONNRESET**，client 0.6–1ms、serve=0（请求头未在连接死前送达），与"服务端却记 200"并存——死的是被放弃的尾挂连接（对应 ADR §5.2 的 8 个尾挂）。
- 佐证：① home（无 viewId，走不同路径、单请求快）从不失败；② 把单请求降到百毫秒级后，**同一 undici 全局池、无任何 Agent/背压改动**，C=8 3401 采样 0 连接失败。故无需显式 Agent 连接池——那只治表；治本是消灭慢请求积压。
- harness 侧补齐：`Sample.errorCode` 沿 undici `cause` 链取 `ECONNRESET/ECONNREFUSED/UND_ERR_*`，`ScenarioStats.errors` 输出失败原因直方图，报告新增"失败原因分布"。传输层失败不再被 catch 吞成裸 status=0（ADR §5.3 的归因缺口闭合）。

## 3. 第二处物理计划劣化：带过滤的 keyset 取页（ADR §3 之外的新点）

ADR §3 与 gate §2 已证明 home keyset / status 等值 / money range 的**计数与裸物理查询**在 50 万行亚毫秒。本轮在 100k 端到端分解时发现 `physicalKeysetOnCreatedAt` 在**带过滤 + 按 createdAt 排序取首页**时仍有独立劣化（与计数同源但取页路径未覆盖）：

- 旧形态：`FROM records r WHERE r.tableId=? AND deletedAt IS NULL AND <相关 EXISTS on rfi> ORDER BY createdAt,id LIMIT 101`。过滤列（money）与排序列（createdAt）不同，SQLite 沿 `records_table_live_created_id` 覆盖索引逐行探测 EXISTS 直到凑够 100 行，100k range（命中 59,787/95,029）冷启动 65s、稳态 5–51s。
- 修复：当该过滤可由 `compileCountPlan` 安全表达（纯合取 / 同字段 OR 的标量正向谓词）时，取页改走 **rfi INNER JOIN 驱动**：`FROM records r JOIN rfi cN ON … WHERE r.tableId=? AND deletedAt … ORDER BY createdAt LIMIT`，EXPLAIN 变为 `SEARCH x USING INDEX rfi_table_field_num` range seek + `SEARCH r USING INDEX sqlite_autoindex_records_1`。
- 实测（100k，热缓存，同一 range 1000..8000，结果同为 100 行）：旧 7.8–51s vs JOIN **0.13–0.32s**。count 快路径此前已修（1650ms→1.5ms，gate 数据为同型）。
- 安全前提与 count 一致：参与 JOIN 的字段必为标量（每记录每字段恰 1 行 rfi），INNER JOIN 不重复计数/取行；NOT 折叠谓词（neq/isNot/isNoneOf）、multiSelect 多行、跨字段 OR、残余过滤一律回退原相关 EXISTS。取值逐值不变由新增对拍锁定：**同字段 range(age gte+lte) T1 keyset 翻页拼接 == legacy 过滤后有序集合**（不重、不漏、序相同、filteredTotal 相等），compileCount 14 个纯函数用例覆盖放弃条件。

同批还消除了 T1（无排序）路径的无条件全量物化：`runKeysetPaging`/`runQueryPlan` 原先对所有查询先跑 `physicalOrderedIds`（全量有序候选），即使 T1 最终走 `pageCreated` 根本不用它；现 T1 完全跳过，A 档无排序分页用新增的 `physicalCreatedPage`（keyset seek 取当页）。仅 T2 排序 / T3 宽口径才物化候选序列。

## 5. harness 可复现性补强（为大库门与固定规格机做准备）

- `--scenes a,b,c` 白名单：不传 = 全量 18 场景（S9 默认不变）；10 万/50 万大库只跑物理门场景，裁掉随行数线性劣化、明确不算 ADR 触发项的 T3 宽口径。
- 深页游标准备：on 档 home_deep 改为 run-gate 用只读连接在覆盖索引上 `ORDER BY createdAt,id LIMIT 1 OFFSET (page-1)*limit-1` 一次性取边界行、按 `cursor.ts` 同格式编码；采样仍打真实 HTTP keyset（测深页单请求稳态延迟，不含逐页累计成本）。修复前 100k 翻到 80% 页需 800 次当页 hydrate、数千秒，整轮被杀；修复后 100k home_deep P95 2763ms 可完成。off/shadow 走 offset 本就不翻页，不受影响。
- 失败原因直方图（§1）使连接类失败与 HTTP 非 2xx、超时可机械区分，满足 T0 的自动对账前提。

## 7. 对 ADR-0008 的影响（仅陈述事实，不替总监置状态）

- §5 / 附录 A 中任务 #84 与"harness C≥8 连接层修复""日志审计脚本"原标 E4；#84 本体（传输错误码 + 根因消除 + T0 复跑）现已完成并有 E2 产物。可脚本化的 `<--`/`-->` FIFO 对账器本轮未单独入库（T0 目前以 JSON errors 直方图 + 日志零尾挂人工核对为准）；如总监要求把 T0 对账做成 CI 机械门，可作为后续小切片补 `scripts/bench/audit-server-log`。
- §3 物理层结论不变且更稳：新增"带过滤 keyset 取页"这一计划点也已走索引、100k 0.3s。
- S10 性能侧是否仍记 INCONCLUSIVE：T0 已解锁，但 ADR §6 设定的 T1 终判仍要求 S5b-Ⅰ/Ⅱ 落地 + `node --cpu-prof` 归因 + 固定规格 4C8G+SSD 上 100 万 best-of-5；这些本轮按 ADR 边界未做，故 100 万终验与端到端 <800ms 签核仍维持"待 S5b 与规格机"，结论走向（不迁 PG）不因此改变。
