## 1. 权限矩阵（可 / 不可 / 无入口）

「可」= UI 操作真实生效；「不可」= 入口存在但置灰或提交被后端拒绝；「无入口」= 界面根本不渲染该入口。

| 操作 | 局外人 | 只读者 | 编辑者 | 库所有者 |
| --- | --- | --- | --- | --- |
| 看到并进入该库 | 无入口 | 可 | 可 | 可 |
| 查看库记录数据 | 不可(403) | 可 | 可 | 可 |
| 新建记录 | 不可(403) | 不可（按钮置灰，API 403） | 可 | 可 |
| 编辑单元格 | 不可(403) | 不可（编辑器能打开，提交 403） | 可 | 可 |
| 删除记录 | 不可(403) | 无入口 | 可 | 可 |

## 2. 越权尝试：绕过 UI 直打 API 的真实状态码

用只读者（阅读者）自己的 JWT 直接打接口：

| 请求 | 方法 | 真实状态码 | 响应体 |
| --- | --- | --- | --- |
| `/api/records/:id` 改一条记录 | PATCH | **403** | `{"error":"当前角色无权编辑数据","code":"FORBIDDEN"}` |
| `/api/records/:id` 删一条记录 | DELETE | **403** | `{"error":"当前角色无权编辑数据","code":"FORBIDDEN"}` |
| `/api/records?tableId=…` 新建记录 | POST | **403** | `{"error":"当前角色无权编辑数据","code":"FORBIDDEN"}` |
| `/api/fields/:id` 删一个字段 | DELETE | **403** | `{"error":"当前角色无权修改表结构","code":"FORBIDDEN"}` |
| `/api/tables/:id/clear` 清空表 | POST | **403** | `{"error":"当前角色无权编辑数据","code":"FORBIDDEN"}` |
| `/api/views/:id` 改视图配置 | PATCH | **403** | `{"error":"该视图已锁定，当前角色无权修改","code":"FORBIDDEN"}` |
| `/api/bases/:id` 改库名 | PATCH | **403** | `{"error":"只有所有者可管理 Base","code":"FORBIDDEN"}` |
| `/api/bases/:id/members` 加成员 | POST | **403** | `{"error":"只有所有者可管理 Base","code":"FORBIDDEN"}` |
| `/api/bases/:id` 删库 | DELETE | **403** | `{"error":"只有所有者可管理 Base","code":"FORBIDDEN"}` |

**没有一次 200**，只读者改记录 / 删字段 **均未成功** → **无 P0 安全越权**。

对照其余身份（同样直打 API）：
- 编辑者：删表 403「当前角色无权修改表结构」；改库名/加成员/删库 403「只有所有者可管理 Base」；清空表 **200**（记录入回收站，可恢复，见 O-1）。
- 局外人：读库 403「无权访问该 Base」；改记录/建记录/清空表/导出 全 403；全局搜索 `/api/search?q=…` 返回空（零泄漏）。

## 3. 项目既定口径回归（无权限不渲染入口，不做 disabled 假入口）

| 只读者：回收站「恢复」按钮 | 可见但置灰 | △ 轻微违反（比假入口轻） |
| 只读者：删除记录 / 新建数据表 | 界面无入口 | ✅ 符合 |
| 只读者：视图下拉「新建/重命名/删除视图」 | 界面无入口 | ✅ 符合 |
| 只读者：文档行菜单「重命名/独立权限/删除」 | 界面无入口 | ✅ 符合 |
| 只读者：库设置「邀请表单/移除按钮」 | 界面无入口（只读） | ✅ 符合 |
| 只读者：无 ACL 文档打开 | 只读渲染，**不显示编辑/保存入口** | ✅ 符合（文档侧做得最干净） |

结论：**数据库侧前端大量「先渲染、后拒绝」**（靠后端 403 兜底），文档/知识库侧做得好。违反项按 P2 登记。

## 4. 局外人（完全未授权）表现

- 登录后左导「暂无数据库或知识库」，**看不到** `WK-权限测试`（perm-08）——入口侧符合口径。
- **手输库视图 URL**：URL 停留在原地址，主内容区**无限转圈**，7 秒后仍无「无权限」提示、无跳转（perm-09 / perm-10）。后端 `GET /api/bases/:id` 正确返回 **403「无权访问该 Base」**，是前端未处理该错误态。
- **手输知识库 URL**：渲染成「还没有内容 / 新建一篇 Markdown 文档…」的**假空态**（perm-11），与实际存在的两篇文档不符，误导为「库是空的」；同一场景手输**文档** URL 却是正确的「没有访问权限」页（perm-12），三处行为不一致。
- 手输库设置 URL、直接打数据 API：全部 403，无数据泄漏；全局搜索命中数为 0。
- 局外人仍可自建库并成为其所有者（perm-13），这是注册用户层面的设计，非越权。

## 5. 文档级 ACL

- 授予方式：KB 首页文档行菜单 → **「独立权限」** → 填成员邮箱 + 角色（可编辑/可评论/仅查看）→ 授权（perm-07）。
- 只读者 KB 角色为「仅查看」，仅对「文档甲-ACL实验」授了「可编辑」：
  - 文档甲：**API PUT `/api/kb/docs/:id/content` = 200**、PATCH 标题 = 200；UI 打开带「编辑/源码/预览 + 保存」区（perm-27/28）。
  - 文档乙-对照组：**PUT content = 403「当前角色无权编辑」**、PATCH 标题 = 403；UI 只读、无编辑与保存入口（perm-29）。
- 结论：**文档级 ACL 真实生效且与库/KB 角色叠加取高者**，UI 与 API 一致，唯独同一 KB 内两篇文档表现截然不同，验证通过。

## 7. 因界面上找不到而无法验证的部分

1. **组织层系统角色（管理员/编辑者/评论者/只读成员）的授权与效果**：「通讯录」「工作区设置」入口只有持组织管理动作的身份可见（perm-42 工作区所有者可见，perm-08/14 我的四种身份均不可见）。本次四种身份**未授予任何组织角色**，所以组织角色轴未走通。
2. **角色授予走的是哪条链路**：库级角色走「库设置 → 成员与权限 → 邮箱+角色 → 邀请」（旧三表 `baseMembers`，perm-04/06）；KB 级角色走「KB 设置 → 添加成员」；文档级走文档行菜单「独立权限」。**组织层角色授予（通讯录 → 角色管理 → 添加成员/部门）只有工作区所有者能进**（perm-43），本次未实操授予。
3. **因权限引擎默认关闭而走不通的**：`AUTHZ_ENFORCE_READY=false` / `GX_AUTHZ_ENGINE=off` → 系统走旧三表决策；`/api/v1/meta` 只返回 `{apiVersion, enterpriseOrg, auth}`，**不下发 `authzManage`**，故「权限管理」页恒只读（已知限制 H-129），其写路径无法验证。
4. **「评论者」档位**未构造身份，评论读写表现未测。
5. 编辑者的**「新建视图」**未逐项确证（默认网格视图对编辑者也是「已锁定」403，未另建视图验证）。
