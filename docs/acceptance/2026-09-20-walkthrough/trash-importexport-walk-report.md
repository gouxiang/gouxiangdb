## 二、回收站走查

### 2.1 已验证通过（全部真机操作）

1. **记录软删（L2）**：抽屉「删除记录」→ 确认弹窗「删除记录「R2」/ 记录会移入回收站，30 天内可恢复。」→ 网格即时少一行 → toast「已删除记录「R2」」带 6 秒「撤销」（shot-t03-delconfirm.png / shot-t04-undo-toast.png）。软删确认用蓝色主按钮、彻底删除用红色——与 R-D-23 的 L2/L4 分级一致。
2. **字段软删**：列头菜单「删除字段」→ 确认文案明示「该列的数据会一并移入」→ toast「已删除字段「待删字段」」带撤销。
3. **表软删**：表操作菜单「删除表」→ 确认「数据表会移入回收站，30 天内可恢复。」→ 侧栏即时移除 + 撤销 toast（shot-t09-tableconfirm.png）。
4. **回收站列表**：类型/名称/所属/删除时间/操作五列齐备，恢复置灰逻辑、彻底删除仅 canManageBase 可见（TrashPage.tsx:147-167，UI 实测按钮齐全，shot-t11-trash.png / shot-t13-trash2.png）。
5. **逐项恢复 + 数据完整性**：
   - 恢复记录 R1 → 名称/数量/备注 全部还原（API 核对：R1/10/备注1/x1）。
   - 恢复字段 待删字段 → 列数据 x1/x2/x3 完整回来。
6. **表级联恢复（关键场景）**：先删记录 R2、再删字段 待删字段、最后删整表 → 回收站只出现「表」一条 → 恢复表后**子树全还原**：字段列表含 待删字段、记录含 R2（API 核对 6 条记录、4 个字段）。与 routes/records.ts 恢复分支注释的级联设计一致。
7. **彻底删除（L4）**：红色确认弹窗，按钮用具体动词「彻底删除」，文案「会被永久删除，不进回收站、不可恢复。」→ 执行后列表即少一条（shot-t15-purge-confirm.png）。
8. **清空回收站**：确认弹窗带具体项数「回收站里的 1 项会被永久删除」→ 空态三要素齐备（图标+「回收站是空的」+次文案+「返回该库」）（shot-t16/17）。

### 2.2 缺陷

#### T-1（P2）恢复不查重名，产生同表重名字段 / 同库重名表

- **复现**（API+UI 双重现实测，夹具已清理）：
  1. 删除字段「待删字段」→ 新建同名字段「待删字段」（201，正常）→ 从回收站「恢复」旧字段 → 返回 `{ok:true}`，表内出现**两个「待删字段」**（API 核对 `names:["名称","数量","备注","待删字段","待删字段"]`；网格渲染两列同名，shot-t18-dupname.png）。
  2. 同法对表：删除「回收走查」→ 新建同名表 → 恢复 → 库内出现**两个「回收走查」**（`tables:[...,"回收走查","回收走查"]`）。
- **后果**：公式 `{待删字段}` 引用歧义；CSV 导入按列名自动匹配歧义；侧栏/页签重名无法区分；后续删除/改名操作目标不明。全程无任何提示或冲突处理。
- **根因**：`apps/api/src/routes/records.ts` restore 路由（`/trash/:id/restore`，约 :795 起）field 分支直接 `prisma.field.update({ data: { deletedAt: null } })`、table 分支直接复活，**均不检查同容器内是否已有同名活实体**；而 `POST /api/fields` 新建路径有「字段名「名称」已存在」409 查重（本人在 #416 期间实测过该 409）。
- **建议修法**（任选其一，推荐 ①）：
  1. 恢复时重名则自动改名并 toast 说明（如「待删字段（已恢复）」「回收走查（恢复副本）」）；
  2. 恢复前弹冲突确认：重名 → 让用户选择「自动改名 / 取消」。
  - table 恢复分支同样处理；field 恢复需注意 links/subtable 反向配对字段同步改名（或保持配对原名+后缀）。
- **建议测试**：同表同名恢复 / 同库同名恢复 / links 字段带反向字段恢复改名。

### 2.3 观察项（不强制修）

- **T-OBS-1（P3）**：表进回收站后，其内此前删除的字段/记录不再单列——行为正确（恢复=整树还原，实测数据完整），但列表条目没有「含 N 条记录 / M 个字段」提示，用户不知道恢复一张表会连带还原哪些东西。建议在「所属」列或名称后加摘要徽标。

## 三、CSV 导入走查

### 3.1 已验证通过

1. **四步向导**：上传（文件/粘贴双入口）→ 字段映射 → 确认 → 执行与结果；步骤条高亮/打勾正确（shot-i01-wizard.png）；空内容时「下一步」正确置灰。
2. **解析正确性**（粘贴 `名称,数量,备注,城市` 3 行刁钻数据）：「张三, Jr」逗号包裹、`"多行\n备注"` 单元格内换行、`"李""四"` 引号转义——映射步预览全部正确（shot-i03-mapping.png）；计数「解析到 4 列 / 3 行数据」正确。
3. **导入结果**：新增记录 3、新建字段 1（城市）、问题行/列 0（shot-i06-result.png）；网格即时出现新列与新行；API 核对取值逐格正确（含换行 `\n` 保留、引号还原）。
4. **显式映射**：`mapping {名字→名称, 队伍→城市}` 导入 2 行，落点正确（赵六→名称/红队→城市）。
5. **类型推断**（新建字段路径）：整数/小数→number、`true/是`→checkbox、`YYYY-MM-DD`→date（实测入职日期列建成 date 且取值正确）、邮箱→email、其余→singleLineText。与 `apps/api/src/domain/csv.ts:154-173` 一致。
6. **确认页**：数据行数/列数/已显式映射数/其余列策略四行摘要清晰（shot-i04-confirm.png）；无表结构权限时的警示文案在码内（ImportWizard.tsx:359-364），受限账号路径未实测（归 #414 权限组合走查）。

### 3.2 缺陷

#### I-1（P2）非法值静默置空，且不计入「问题行/列」

- **复现**：数量列第三行为 `abc` → 导入结果「新增 3、问题 0」；API 核对该行 `数量: null`。同理实测：单选列「超高」（选项外值）不报错（该列被推断为文本所以成立）；json 列非法串会走 `csv.ts:196-201` 同样静默 null；checkbox 列「maybe」会静默 false。
- **口径冲突**：R-I-18 明确「失败行不静默丢弃」，UI 也宣称「错误明细（失败行不静默丢弃）」——但 cell 级静默丢值使用户无从知晓「abc 没进去」。行级事务回滚路径（applyFieldWrites 抛错→errors.push）是有的，但数字/JSON 强转不抛错。
- **根因**：`apps/api/src/domain/csv.ts:176-204` `coerceCellValue`——`Number("abc")`→NaN→`return null`（:186-188）；`JSON.parse` 失败→null（:196-201）；checkbox 其它值→false（:190）。
- **建议修法**：`csv-import` 路由循环里把「非空值强转结果为 null/false 且原文非空」的 cell 记入 `errors`（如「第 3 行「数量」的值 abc 不是合法数字，已留空」），不中断导入。这样「下载明细」按钮也才有真实用武之地（本次走查因 errors 恒空未能实测下载明细）。

### 3.3 观察项

- **I-OBS-1（P3）**：自动新建字段不会推断出 singleSelect——「高/超高」两值建成 singleLineText。低优先级：可加「重复值≥N 且去重后≤M → singleSelect」启发式，或在映射步允许用户指定新字段类型。
- **I-OBS-2（P3，登记未测）**：文件按 UTF-8 文本读取（`file.text()`），Excel 另存的 GBK/GB18030 CSV 会乱码、带 BOM 的表头首列名会含 BOM。建议：读入后剥 BOM；乱码提示或文档说明「请另存为 CSV UTF-8」。
- 重复导入不做去重（同 CSV 导两次=两份记录），符合「导入即插入」预期，仅提示文档写明。

## 四、CSV 导出走查

### 4.1 已验证通过

1. **弹窗结构**：范围（当前视图=默认勾选、按视图筛选排序说明；全部数据）、格式（CSV 实选 + Excel「规划中」徽标）、附件（规划中）——不提供假按钮，符合 R-N-17（shot-e01-exportdlg.png）。
2. **规划中点击反馈**：点「Excel（.xlsx）」→ toast「Excel 导出 · 规划中，尚未开放」（shot-e02-planned-toast.png）。
3. **CSV 内容正确性**（API 直调 `/api/tables/:id/export.csv` 核对）：表头=字段名；逗号/引号/换行单元格全部按 RFC 4180 转义（`"张三, Jr"`、`"多行\n备注"`、`"李""四"`）；CRLF+UTF-8；`Content-Disposition: attachment`。

### 4.2 缺陷

#### E-1（P3）导出文件名用 tableId，用户无法辨识

- 现象：下载名为 `table-cmu900ge90003se3r3e8paq7e.csv`（服务端 `Content-Disposition` 同样是 id）。
- 根因：`apps/web/src/features/grid/GridView.tsx:436` `a.download = \`table-${tableId}${scope === "view" ? \`-${viewId}\` : ""}.csv\``。
- 建议：前端已有表名（GridView 上下文），改为 `\`${tableName}.csv\``（视图范围可 `\`${tableName}-${viewName}.csv\``）；服务端 Content-Disposition filename 一并带上表名更佳。
