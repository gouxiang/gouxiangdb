## ★ 契约一：一级导航的「数据库 / 知识库」分组仍然存在，只是不画线

### 结论先说

**功能与数据层面，库依然按「数据库组」和「知识库组」分割。本次只是去掉了分组标题行和左右分割线的视觉呈现。**
企业工作台形态下，菜单被横线切成两块会显得突兀、割裂，视觉上应读作连续的一条库列表。

### 真实代码在哪

| 位置 | 说明 |
|---|---|
| `apps/web/src/features/workspace/PrimaryNav.tsx` | `GroupHeaderRow` 组件；行类型 `kind === "group"` |
| `apps/web/src/features/workspace/lib/menu-sections.ts` | `buildLibraryRows(bases, kbs)` 产出含 group 行的列表 |

关键点：真实实现里**分组是数据行**（`kind: 'group'`），且**已有现成的过滤能力**——
`collapsed` 折叠档（R-N-07，56px 只留图标）时执行 `all.filter((r) => r.kind !== "group")`。

### 落地时怎么做

**只需改渲染，不要动数据源。** 推荐加一个显式开关 prop，而不是就地删 group 行，这样语义来源始终可追溯：

```tsx
/** 是否渲染分组标题行（「数据库」「知识库」）。
 *  企业工作台形态默认 false —— 分组在数据层依然成立，仅表层不做视觉体现。
 *  切勿因此删除 buildLibraryRows 里的 group 行：排序分段依赖它。 */
showGroupHeaders?: boolean;
```

```tsx
const rows = useMemo<LibraryNavRow[]>(() => {
  const all = buildLibraryRows(bases, kbs);
  // 折叠档与「不显示分组标题」档都跳过 group 行，数据源保持不动
  return collapsed || !showGroupHeaders ? all.filter((r) => r.kind !== "group") : all;
}, [bases, kbs, collapsed, showGroupHeaders]);
```

**不要直接改 `buildLibraryRows` 去掉 group 行** —— 那才是真正的"分组取消"。

### 千万不要这么理解（反例）

| ❌ 错误理解 | 后果 |
|---|---|
| 「UI 上看不到分组了，说明分组取消了」 | 会把 `kind: 'group'` 行从数据源删掉，排序分段丢失 |
| 「既然不分组了，可以把两个列表合并后全局按名称排序」 | 破坏分组语义，数据库与知识库交错混排 |
| 「分组标题节点没用了，CSS 也一起删」 | 将来恢复分组要重写样式；本原型保留 `.rail-grp` 样式未删 |

### 分组信息保留在哪

原型渲染时每项输出 `data-grp="base|kb"`，分组边界完整留在 DOM 里（只是没有视觉线）。
正式实现同理：group 行保留在数据里，自动化测试与无障碍可据此断言分组顺序，
将来要做「分组折叠」「分组级权限/配额统计」或恢复分组标题时，直接读这份数据即可。

### 将来要恢复视觉分组

渲染回分组标题行即可，数据源与 `data-grp` 都不用改（`.rail-grp` 样式在 `shared.css` 中保留未删）。

### 如果想留一点分组的秩序感

**用留白，不要用线。** 分组切换处加 8–10px 间距即可——线是显性的"分区声明"，留白只是节奏感。

## ★ 契约二：顶带三要素（同高、同线色、中心共线）

顶部横带由三段拼成：左轨 logo 区、二级面板头 `.l2-h`、主区顶栏 `.topbar`。这三者必须：

1. **同高**：统一 56px（此前二级头 52px，与顶栏错开 4px 断差）；
2. **同线色**：底边线统一用同一线色令牌（此前二级头用淡一档，导致同一水平线左浅右深）；
3. **中心共线**：三者的内容垂直中心同在 28px（靠左轨顶部留白 10px 对齐）。

> 这类 4px 断差目视说不出来，但一定量得出来。**怀疑不齐时先量三条：bottom 差、border 色、center 差。**

## ★ 契约三：交付形态 = 底板 + 规范 + 状态矩阵，不做逐页页面稿

### 定论

**不要把所有功能操作页面全部画出来。** 采用「底板 + 规范 + 状态矩阵」，问题最少。

### 依据一：这条路本项目已经走过，并已被否掉

UI-SPEC 修订记录（第 639 行）原文：

> [2026-09-19 v1.0] 改为「规范 + 架构图」单文件交付；**逐页页面稿方案废弃**；`01`–`10` 归档至 `_archive/`。

即「把所有页面全设计出来」曾是既定方案，实践后被废弃并归档。不要重复踩这个坑。

### 依据二：真正的缺口是「状态」，不是「页面」

页面是**实例**（可无限枚举），状态是**模式**（有限集合）。
30 张静态页面稿，每张只画了 1 个默认态，覆盖率反而最低；
而「组件模式 × 状态」的矩阵是有限的，覆盖它才等于覆盖所有页面：

| 模式 \ 状态 | 空 | 加载 | 错误 | 无权限 | 选中 | 溢出 | 拖拽 |
|---|---|---|---|---|---|---|---|
| 列表行 | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
| 工具条 | ○ | — | — | — | ○ | ○ | — |
| 卡片 | ○ | ○ | ○ | ○ | — | ○ | — |
| 菜单项 | — | — | — | ○ | ○ | — | — |
| 弹窗 / 抽屉 | ○ | ○ | ○ | — | — | ○ | — |

（○＝必须给出可点击原型片段；—＝该组合不适用）

当前底板已覆盖「模式」（令牌 / 外壳 / 导航），**尚缺的是这一层状态矩阵**——
它才是实现者会各自发挥、最终导致不一致的地方：空态、加载态、错误态、无权限态、
批量选中后工具条怎么变、字段太多/名字太长/筛选条件过多怎么办、拖拽中长什么样。

### 依据三：原型代码不可复用，画得越细沉没成本越高

本目录产物是**自包含单文件 HTML**（CSS 内联、无跨文件引用），
其 DOM 与样式**一行都无法进入 React 组件体系**（Plait 画布、虚拟滚动、`gx-*` Tailwind 类名）。
原型越细，落地时"原型能做、真实组件做不到"的落差越多 → 返工与对齐成本反而上升。

### 依据四：静态稿必然腐化

产品仍在迭代（离线同步、审批流、权限分区都在动）。
几十张静态稿会过期，成为"第二份 truth"，**制造**不一致而非消除不一致。

| 令牌 | 规范附录 A.1 参考设计值 | v6 底板当前值 | 冲突 |
|---|---|---|---|
| 主色 | `gx-accent` = **#3A6DF0** | `--brand` = **#2c7be5** | ✅ 是 |
| 内容区底 | `gx-bg` = **#F7F9FC** | `--bg` = **#f4f6fa** | ✅ 是 |
| 发丝线 | `gx-hairline` = **#E9EFF9** | `--line` = **#e7eaf0** | ✅ 是 |

UI-SPEC 第 28 行明确：「**不完成这一步，后续所有页面写出来都不会与参考设计一致**」，
且令牌迁移被列为「阶段 0 · 开工前置，必须最先完成」。

**也就是：不管采用哪种交付方式，令牌迁移都得先落。** 否则"依据底板重做"出来的页面跟底板是两套色。

### 落地要求（照 UI-SPEC 附录 A 执行）

- 改 `packages/design-tokens/src/colors.ts`：主色 `#378ADD → #3A6DF0`，中性色迁到冷灰体系
- **包名与 Tailwind 类名保持不变，只换底层取值**并补齐缺失令牌
- 参考设计未覆盖的语义色（success/warning/danger）**沿用现有值，禁止新增**
- 同步回灌 v6 底板，使原型与规范严格同源

## ★ 契约四：原型构建方式

- 源码在 `src/`：`shared.css`（令牌与外壳）+ `*.part.html`（每页片段）+ `build.mjs`（生成器）
- 产物是根目录的自包含单文件 HTML，CSS 内联、无跨文件引用——
  因为预览面板按文件单独托管，跨文件相对引用会 404
- **改完必须跑 `node src/build.mjs` 重新生成产物**
- 生成器用 `import.meta.url` 相对自身定位源码，不依赖当前工作目录
  （重活请走 VM15 `192.168.31.15`，本机 16GB 不跑大内存动作）
