# 构想工作台 · 可自定义 UI 框架（主题功能）可行性调研

> 2026-10-20 ｜ 状态：**调研结论，待戴总拍板** ｜ 不含实现代码
> 所有数字均为实测（`grep` / 文件亲读），口径写在每项后面，可复现。

---

## 0. 结论先行

**建议：采用「CSS 变量契约」路线，但必须分三期落地；现阶段只做第一期与第二期（变量化 + 内置主题一键切换），暂不对外开放"开发者自由定制主题"。**

三条理由：

1. **变量化本身是净收益**：即便最后不做主题，把视觉取值从"构建期常量"变成"运行时变量"，也能让 UI v2 重设计的改色成本从「改代码 + 重新构建」降到「换一组变量」。这笔账单独成立。
2. **对外开放的成本是内置主题的 3~5 倍，且当前不具备条件**：外部定制要求令牌契约长期冻结 + 版本兼容 + 缺键回退 + 对比度校验 + 回归测试；而当前**连一份统一的令牌契约都不存在**（存在两套并行且已不一致的色彩定义，见 §2.3）。契约未定型就对外开放，等于把技术债转嫁成对外承诺。
3. **存在一块主题化覆盖不到的区域**（画布 / 富文本，§3-N3）。内置主题可以靠手工适配兜住；一旦对外开放，用户会发现"换肤后一半界面没跟着变"，这是口碑风险。

## 2. 现状盘点（实测）

### 2.1 有利面：样式纪律执行得非常好

| 指标 | 实测值 | 口径 | 对主题的意义 |
|---|---|---|---|
| `gx-*` 令牌类使用 | **5465** 处 | `grep -Eo "\b(bg\|text\|border\|ring\|shadow\|rounded\|fill\|stroke)-gx-"` | 调用点收敛，改造是"改定义"而非"改 5465 处调用" |
| Tailwind 原生色类（gray-500 等） | **0** 处 | 同上，非 gx 前缀 | 没有游离于令牌之外的颜色 |
| `dark:` 变体 | **0** 处 | `grep -Eo "\bdark:"` | 无历史包袱，但也意味着**零暗色基础** |
| snapshot 测试 | **0** 个 | `grep -rl "toMatchSnapshot"`（共 178 个测试文件） | 改样式不会破坏快照断言 |
| 硬编码 hex | 183 处 / 33 文件 | `grep -Eo "#[0-9A-Fa-f]{6}"` | 见 §2.2，多数不属于主题范畴 |

**这是本项目做主题最重要的资产**：一个几乎 100% 走令牌的样式体系。

### 2.2 硬编码 hex 的真实构成（不能笼统说"183 处待清理"）

| 类别 | 数量 | 位置 | 性质 |
|---|---|---|---|
| 测试断言 | ~80+ | 各 `*.test.tsx`（grid-table-polish、field-select-modal 等） | 非生产代码 |
| 用户可选内容色板 | 36 + 28 | `ColorPicker.tsx`、`features/kb/canvas/canvas-colors.ts` | **业务数据**，用户自选颜色，主题不得改写 |
| 生产主题色 | ~20 | `ui.tsx`(20 含注释)、`icons.tsx`(6)、`PlannedBadge.tsx`(5)、`WysiwygEditor.tsx`(2) | 需纳入令牌 |
| 字段类型色 / 头像色板 | 24 + 8 | `colors.ts` 的 `FIELD_TYPE_COLOR` / `AVATAR_PALETTE` | 数据语义色，可微调但需保持可区分 |

→ **真正需要主题化的生产硬编码约 20 处**，远小于表面数字。

### 2.3 ⚠️ 意外发现：存在两套并行且已不一致的色彩定义

| 来源 | 文件 | 主色 | 覆盖范围 |
|---|---|---|---|
| TS 常量（`as const`） | `packages/design-tokens/src/colors.ts:8` | `#3A6DF0` 冷灰蓝 | 全局（5465 处 Tailwind 类） |
| CSS 变量（带 fallback） | `apps/web/src/features/kb/kb.css:14-26` | `#378ADD` 暖灰蓝 | 仅知识库模块（富文本 / `.md-preview` / `.kb-rich-*`） |

产物 CSS 中实测 **180 处 `var(--gx-*)`**，全部来自 `kb.css`。

**影响**：
1. kb 模块与全局主色已是两个色号（视觉不一致，属既有技术债）；
2. 主题化若只改 `colors.ts`，知识库富文本区域**不会跟着变**；
3. 这层变量写法（`var(--gx-accent, #378add)` 带 fallback）恰好是主题化想要的形式——**先例是好的，只是没推广、且值过期了**。

**处置**：第一期必须先收编这 13 个变量进统一契约，否则主题是"半拉子"。

### 2.4 关键机制：令牌是"构建期常量"，不是运行时变量

- `colors.ts` 用 `as const` 导出 → `tailwind.ts` 映射进 `theme.extend.colors` → Tailwind **3.4** 在构建时把 `bg-gx-accent` 编译成 `background-color:#3A6DF0`
- 结果：**现在改主题必须改 TS + 重新构建，运行时无法切换**

| 事实 | 值 | 影响 |
|---|---|---|
| Tailwind 版本 | 3.4（`apps/web/package.json:63`） | 非 v4，无原生 `@theme`；但支持 `rgb(var(--x)/<alpha-value>)` 写法 |
| 构建产物 CSS | 132 KB | 变量化后体积变化很小 |
| API 侧 | `package.json` 声明依赖但 `apps/api/src` 实测 0 处引用 | 主题化不影响后端 |

## 3. 技术难点（按处置难度排序）

### N1 · 71 处透明度修饰器 —— 必解，方案明确
`bg-gx-surface/90`、`border-gx-danger/40`、`ring-gx-accent/40`（实测 71 处）。
Tailwind 3 无法对 `var()` 做 alpha 运算，必须把颜色变量从 `#FFFFFF` 改为通道值 `255 255 255`，
配合 `rgb(var(--gx-surface) / <alpha-value>)`。
连带：`successBg: "rgba(29,158,117,0.10)"` 等 5 个 rgba 常量需改写为通道形式。
**影响面**：`colors.ts`(106 行) + `tailwind.ts`(143 行) 全部色值重写；**调用点 5465 处一行不改**。

### N2 · 16 个文件的运行时 JS 取色 —— 必解，且最易被忽略
`colors.ts` 是 TS 常量，构建期内联进 bundle。切换 CSS 变量后，这些位置仍显示默认主题色：
`FIELD_TYPE_COLOR`（字段类型色）、`AVATAR_PALETTE`（头像取色）、`CreateLibraryModal`、`ui.tsx`、`KbListPage`、`WorkspaceTopBar`、`PersonalCenterDrawer` 等。
**影响面**：16 个文件需改为从运行时读取（主题上下文 或 `getComputedStyle`）。

### N3 · 画布 / 富文本（Plait 系 8 个包）—— 最大不确定性，无法根治
`@plait/core|common|draw|layouts|text-plugins` + `@plait-board/react-board|react-text|markdown-to-drawnix`。
实测：**Plait 包内 0 个 CSS 文件、0 个 CSS 变量** —— 它的颜色由 JS 运行时传值（SVG / canvas 渲染），
**完全不受 CSS 变量控制**。
**后果**：主题切换后，画布编辑器、富文本内部、Drawnix 自带色板不会跟着变，除非逐个把颜色经 API 传入并触发重渲染。
**处置**：只能做到"容器与外框跟随主题，画布内容靠适配参数兜住"。这是本报告最硬的技术边界，**不因方案选择而改变**。

### N4 · 令牌契约的长期兼容 —— 对外开放才需要，成本最高
外部主题包引用令牌名；一旦我们新增/重命名/删除令牌，旧主题包就会部分失效。
需要：契约冻结 + 语义版本 + 缺键回退 + 变更弃用期。**这是"对外开放"相比"内置主题"多出来的主要成本。**

### N5 · 暗色主题不是"换色" —— 建议与换色主题分开评估
`layout.ts:48-53` 的阴影是硬编码 `rgba(0,0,0,x)`；暗色下阴影需反转。
画布、图表、行色、语义色（`successBg` 等 0.1 透明度）在暗底上都要单独调。
→ "一键切换浅/深"比"一键切换配色"高一个数量级。**建议本期只做换色，暗色单独立项。**

### N6 · 分发与持久化
- Web：主题偏好若要跟随账号，需新增用户偏好存储（只增迁移，项目现有 41 个迁移，属常规操作）
- 桌面壳：`apps/desktop` 的 Tauri 壳做同源反代，外部主题文件如何加载需壳层配合（或内置主题目录）
- **建议**：第一期只落 `localStorage`，不碰服务端，把改动面压到最小

### N7 · 可访问性门禁
自定义主题可能产出不可读组合（浅字浅底）。需最小对比度校验（WCAG）。
内置主题可以人工保证；对外开放则必须自动化校验。

### N8 · 测试与门控
178 个测试文件、0 snapshot → 改样式不破断言（利好）。
但新增主题机制会带来新测试文件，需同步更新「vitest 收集数恒等」门控基线（四门之一）。

### N9 · 结构锚点缺失（见 `CORE-SKELETON.md` §5）
当前没有 `data-region` / `data-state` 之类的语义锚点，主题只能改值、不能改密度与层级。
若希望主题能调"疏密"，需先补锚点（纯新增 `data-*` 属性，不改逻辑）。

## 4. 三条技术路径对比

| 路径 | 做法 | 运行时切换 | 外部可扩展 | 改造量 | 结论 |
|---|---|---|---|---|---|
| **A. CSS 变量契约** | 令牌改为 `var(--gx-*)`，主题 = 一组变量覆写 | ✅ 即时，不重新构建 | ✅ | 中（N1/N2/N3） | **推荐** |
| B. 多套构建产物 | 每主题构建一份 CSS，切换时换 `<link>` | ⚠️ 需加载另一份 CSS | ❌ 只能内置 | 低（但产物 ×N） | 备选 |
| C. 运行时 CSS-in-JS | 引入 emotion/styled 等 | ✅ | ✅ | **极高**（违反"禁新依赖"，且要重写 5465 处） | 否决 |

路径 B 适合"只要两三个内置皮肤、且不想动令牌层"的最小实现，但**与"开发者自由定制"的诉求不兼容**，只能作为 A 未落地前的临时方案。

## 7. 建议路线（三期）

| 期 | 目标 | 产出 | 验收标准 | 是否建议现在做 |
|---|---|---|---|---|
| **一期** | 令牌变量化（不含任何新功能） | 统一 `:root` 变量层、收编 kb.css、解决 71 处 alpha、16 处运行时取色改读变量 | **视觉零变化**，四门全绿；产物 CSS 中 hex 显著减少 | ✅ **建议** |
| **二期** | 内置主题 + 一键切换 | 2~3 套内置主题（含 UI v2 的「墨白 Ink」）、切换入口、localStorage 持久化 | 切换即时生效、刷新保持、画布外全部跟随 | ✅ **建议** |
| **三期** | 对外开放开发者定制 | 令牌契约文档 + 主题包格式 + 导入/校验 + 对比度门禁 | 第三方主题可导入且不会把界面弄坏 | ⚠️ **二期验收后再议** |

**一期必须先行**：它把"能不能主题化"这件事从猜测变成事实——如果一期做完发现视觉有偏差，说明契约设计有问题，此时修正成本最低。

---

## 8. 明确不建议的事

1. **不建议现在就承诺"开发者自由定制"**：契约未冻结、画布无法跟随、校验机制未建，三项前置都不成立。
2. **不建议本期做暗色主题**：它不是换色，是另一套设计（N5），应与换色主题分开立项。
3. **不建议引入 CSS-in-JS 依赖**：违反项目"禁新依赖"约束，且要重写 5465 处调用点。
4. **不建议改 5465 处调用点**：改造应全部收敛在令牌定义层，这是本次可行性成立的前提。
