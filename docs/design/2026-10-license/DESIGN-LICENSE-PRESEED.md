# 正版授权机制 · 预埋设计（License Pre-seed）

> 状态：**未来计划 / 预研稿，本期（0.2.5-beta）不落地任何产品代码改动**
> 日期：2026-10-19
> 适用产品：构想工作台（GouXiangDB）—— macOS 桌面壳（apps/desktop, Tauri v2）+ 自托管后端（apps/api, Hono+Prisma+SQLite）+ 飞牛 fnOS 包（fpk）
> 决策来源：戴总 2026-10-19 拍板——「商业化加固列入未来计划；下版本想办法在**不影响当前代码**的情况下加入正版授权机制，暂时不一定生效，但要提前预埋做预防」。

---

## 0. 给非技术同学的一句话

我们在软件里**提前留好"授权检查"的插槽和电线，但这个插槽出厂时是"直通"状态（什么都不拦）**。将来要卖正式版时，只要把开关打开、配上授权服务器，就能启用"试用 / 激活 / 到期"等能力，**不需要回头大改架构**。本期它完全隐形、不改变任何现有功能、不联网、不收集任何信息。

---

## 1. 目标与非目标

### 1.1 目标
1. **提前预防**：在架构上预留授权相关的接缝（seam），把"以后要加授权会动到主干"的风险降到最低。
2. **默认不生效**：所有预埋默认 **off / 旁路（bypass / fail-open）**，与当前已发布行为逐字节等价。
3. **小步、增量、旁路、可回滚**：严格遵守项目最高硬约束——新功能＝增量、旁路、默认关闭、不动旧数据。
4. 形成一份**可分阶段实施**的路线，明确"哪些钩子现在埋、哪些能力将来做"。
5. 诚实界定**本地授权的能力边界**（防君子、提升盗版门槛），不夸大保护强度。

### 1.2 非目标（本期及预埋阶段都不做）
- 不做强制激活、不做联网鉴权、不做功能锁死（kill switch）。
- 不收集机器指纹、不上报任何遥测/心跳。
- 不做代码混淆/加密（那是独立的"源码保护"议题，见 §9 附录，与授权解耦）。
- 不改数据库表结构、不动迁移、不影响存量用户与离线内测。
- 不引入任何新的第三方 npm 依赖（web 端硬约束）；Rust 侧密码学优先用既有依赖链（见 §7.3）。

## 2. 设计原则（不可妥协）

| 原则 | 含义 |
|---|---|
| **默认旁路 fail-open** | 开关缺省/缺失/异常时，一律"视为已授权、正常放行"，绝不能因为授权模块的小问题挡住正常用户。 |
| **零行为变化** | off 态下，不新增网络请求、不新增文件、不新增弹窗、不改变启动时序与性能（可被现有四门 + golden 证明）。 |
| **单点判定 + 单一出口** | 授权结论只由一个纯函数/一个命令产出，所有消费点只读它的结论，禁止各处自行判断（对齐项目"唯一出口"纪律）。 |
| **配置即开关** | 复用现有 `GX_*` 环境变量/配置闸门范式（参照 `GX_SYNC_SERVER`、`GX_M5_SEARCH`、`GX_POC3`），不发明第二套开关体系。 |
| **数据只增不碰旧** | 将来需要存授权状态时只新增独立文件/表，不写进现有 dev.db 业务表，不影响备份与同步。 |
| **可独立拆除** | 授权是可插拔模块，理论上删一个目录 + 注销一行注册即可彻底移除，不反向污染业务代码。 |

## 4. 威胁模型与能力边界（务必先认清）

授权机制要回答的是"**谁、在哪台机器、被允许用到什么程度**"。但因为产品是**交付到用户自己机器上的本地软件 + 可自托管的后端**，必须诚实：

1. **纯本地校验只能提高门槛，不能杜绝破解。** 攻击者可读取/修改明文 JS、patch Rust 二进制、伪造系统时间、重放许可文件。因此保护强度排序应是：
   **关键能力/规则放服务端（最强） > 带签名的离线许可（中等） > 纯本地标志位（最弱，只防误操作）。**
2. **自托管后端在客户自己服务器上**，无法靠"我方服务器在线"来卡授权。对飞牛/私有化部署形态，授权更适合"**许可文件 + 到期/容量/席位声明，签名防伪造**"，而不是强制联网激活。
3. 因此本方案的定位：**确立合法使用边界、形成商业化计费抓手、让善意客户易于合规、让盗版有明确成本**，而不是"绝对防破解"。
4. **绝不能因授权问题导致用户数据被锁死或丢失。** 即使许可过期，数据导出/备份/可读必须保留（见 §8 红线）。

## 5. 授权模型（将来生效时的目标形态）

### 5.1 三种凭证形态（按部署形态）
| 形态 | 适用 | 凭证 | 是否需联网 |
|---|---|---|---|
| **试用 Trial** | Mac 桌面个人版 | 首次运行生成的本地试用态（宽限期），无需任何账号 | 否 |
| **离线许可 License File** | Mac 正式版 / 飞牛私有化 / 自托管 | 一份我方**私钥签名**的许可文件（`.gx-license`，JSON+签名） | 激活时可选联网；平时离线有效 |
| **订阅激活（远期可选）** | 将来若做云授权/按年订阅 | 激活码换短期令牌，落钥匙串，定期续期 | 是（但默认不强制，留作可选通道） |

### 5.2 许可文件声明的字段（建议，additive）
- `product`（如 `gouxiangdb-desktop` / `gouxiangdb-fnos`）
- `edition`（如 `personal` / `team` / `enterprise`）
- `licensedTo`（客户/组织名，便于 UI 展示归属）
- `seats`（席位数，team/enterprise 用；个人版可省）
- `issuedAt` / `expiresAt`（可空＝永久；订阅版到期）
- `maxBases` / 功能位 `features{}`（将来按版本做能力分级，如离线同步、MCP、向量检索）
- `fingerprint`（可选，绑定机器/设备；私有化可绑服务器指纹，个人版可不绑以减摩擦）
- `licenseId` / `nonce`（唯一与防重放）
- 外层 `signature`（用**与更新签名一致的非对称密钥体系**签发，公钥内置/可配置，私钥永不进客户端）

> 字段全部 **additive、可空**；旧版本读到不认识的字段应忽略而非报错（与项目 additive 演进纪律一致）。

### 5.3 单一判定结论
授权模块对全系统只输出一个枚举结论（建议）：
```
type LicenseVerdict =
  | { kind: "bypassed" }                 // off 态/未启用：唯一在本期出现的结论
  | { kind: "trial"; daysLeft: number }
  | { kind: "licensed"; edition: string; expiresAt: string | null }
  | { kind: "grace"; reason: string; daysLeft: number }   // 宽限，不硬锁
  | { kind: "expired" } | { kind: "invalid"; reason: string };
```
**本期任何代码路径拿到的永远是 `{kind:"bypassed"}`。**

## 6. 分阶段实施路线（钩子先埋，能力后开）

> 每阶段都满足：默认 off、四门证明零变化、独立可回滚、只增不改旧。

### 阶段 L0（本设计稿，0 产品代码）—— 现在
- 仅产出本文档，统一术语、字段、判定枚举、挂接点、红线。
- 不建表、不加依赖、不改启动流程。

### 阶段 L1（下版本可做的"纯预埋"，仍 100% 不生效）—— 推荐的"提前预防"落点
目标：把**接缝和纯函数**放进去，但出厂结论恒为 bypassed。

1. **Rust 侧新增独立模块** `src-tauri/src/license/`（新目录，不塞进现有文件）：
   - `types.rs`：§5.3 的 verdict 枚举（先只构造 `bypassed`）。
   - `gate.rs`：**纯函数** `evaluate(env, store, now) -> Verdict`。本期实现为：读 `GX_LICENSE_MODE`，缺省/`off`/无法识别 ⇒ 一律 `Bypassed`；任何错误 ⇒ `Bypassed`（fail-open）。配 headless 单测钉死"off 恒 bypassed、异常也 bypassed"。
   - 不注册插件、不联网、不读不写任何文件（off 态）。
2. **注册一条只读 Tauri 命令** `gx:license_status`（加入 `main.rs:131` 的 handler 列表）：内部调用 gate，off 态恒返回 `{kind:"bypassed"}`。命令存在但**前端本期不调用、不展示**。
   - 这是"预埋电线但不通电"：接口形状冻结，将来通电不动前端契约。
3. **后端配置占位**（`apps/api/src/config.ts`）：增加 `GX_LICENSE_MODE`（默认 `off`）与可选 `GX_LICENSE_PUBLIC_KEY`（默认空），带单测；**不挂任何强制路由**。可另加一个**只读** `GET /api/v1/license/status`，off 态返回 `{mode:"off"}`，不鉴权也不泄露敏感信息（或干脆本期不挂路由，仅留配置）。
4. **不建数据表、不写盘、不联网**。L1 的全部可观测差异只有：多了一个恒返回 bypassed 的命令与几个默认 off 的配置项。

> L1 验收（四门 + 零变化）：vitest 收集数恒等；三包 tsc 0；eslint 0 error；S0 golden 不变；新增的 gate 单测全绿；实测 off 态启动时序/网络请求/文件系统与旧版一致（可用现有 PoC headless 框架对拍）。

### 阶段 L2（商业化启动时才做：离线许可最小闭环）
- 定义并冻结 `.gx-license` 的 JSON+签名 schema；选定签名算法（见 §7.3）。
- gate 在 `GX_LICENSE_MODE=verify` 时：定位许可文件（Mac 用安全存储/应用支持目录；fpk 用挂载目录内约定路径）→ 验签 → 校验有效期/产品/可选指纹 → 出 verdict；任何异常进入 **grace（宽限）而非硬锁**。
- UI 呈现：启动器/设置区"已授权给 X / 到期日"，试用剩余天数；过期仅给温和提示与导出入口，不碰数据。
- 配我方**签发工具**（离线脚本，私钥保管在发布机/钥匙串，绝不入仓、不入客户端）。
- 仍然默认 off；只有明确打"商业版"构建/配置时才 verify。

### 阶段 L3（远期，按商业模式决定是否做）
- 可选联网激活/订阅续期（激活码换令牌、落钥匙串、可离线宽限 N 天）。
- 按 edition/feature bits 做功能分级与容量（席位/库数量）门控。
- 服务端签发/吊销/续费管理后台（可复用现有的 Gitea/托管设施，不与更新通道耦合）。
- 与 §9 的**源码保护**组合，提升整体门槛。

## 7. 关键技术决策（预留意见，落地前再审）

### 7.1 开关命名与默认值（对齐现有范式）
- `GX_LICENSE_MODE=off|verify|enforce`（默认 `off`）。
  - `off`：bypassed（本期、内测、自托管开源用户）。
  - `verify`：验签但**只提示不阻断**（L2 软落地/影子期，便于观察）。
  - `enforce`：真正按授权收敛（L3，且仍保留 grace 与数据导出，见 §8）。
- 永不新增"删除/上报"类开关；只有判定姿态。

### 7.2 时钟与防回拨
- 纯本地无法可靠防改系统时间。L2 只做"记录最近一次见到的时间"这类**轻提示级**检测，发现回拨进 grace 并提示，不据此删数据。强约束留给服务端形态。

### 7.3 签名算法
- 优先**与 Tauri updater 已用的 minisign/Ed25519 体系保持一致**（updater 已走 minisign 验签，PoC-3 验证过链路），减少新密码学依赖与密钥管理面。
- 复用项目 Rust 安全闸门经验：谨慎选 crate、跨平台用平台信任根；新增原生依赖必须过"构建可重复 + 安全审查"，并核查是否引入 aws-lc-rs 等重依赖（项目红线：能用既有/轻量就不引重库）。

### 7.4 机器指纹（可选，默认不采集）
- 仅在 `enforce` 且客户接受绑定时才计算，使用**非敏感、稳定、不可逆**的硬件/卷标识派生哈希；采集前在 UI 明示。个人零售版默认**不绑机**以降低正版用户的激活摩擦（摩擦过大反而伤害付费转化）。

### 7.5 与"自动更新"的关系
- 授权与更新是**两条独立通道**。beta/rc 走 Gitea prerelease（**不带 update-manifest.json 资产**，稳定版用户不可见——0.2.5-beta.1 即如此发布）；将来商业版可在许可里区分可接收的更新通道，但不耦合发布脚本。

## 8. 红线（任何阶段都不许违反）

1. **fail-open 优先**：授权子系统自身任何故障/缺配置/解析失败，不得阻断正常启动与使用（进入 bypassed 或 grace）。
2. **数据安全高于授权**：许可过期/无效时，**绝不删除、不加密、不上传、不锁死用户数据**；必须保留只读与导出/备份能力。
3. **默认 off、零外联、零遥测**：未显式启用前，不发起任何网络请求、不采集指纹、不写授权文件。
4. **私钥永不入仓、永不进客户端**；只在发布机/钥匙串保存，签发动作与构建分离。
5. **不影响四门与既有 golden**；每个 L 阶段独立提交、可单独回滚。
6. **不与 jwt-secret / 业务 dev.db 混用存储**；授权状态独立存放。
7. 对内测、自托管、开源用户长期保留 `off` 形态，避免"测试版/自家部署被自己的授权挡住"。

## 9. 附录：商业化加固（议题登记，与授权解耦，本期只规划）

> 戴总 2026-10-19 关切的另两点：删 App 是否留孤儿进程、封包是否泄露源码。现状结论与未来加固登记于此，**本期不改**。

### 9.1 进程/卸载（现状已基本健康，记录在案）
- 现状实测（0.2.5-beta）：内核 gxnode 是壳的**子进程**、同进程组；已做外部 SIGTERM/SIGINT 收尸（R2，main.rs reaper）；**无 LaunchAgent/Daemon/登录项**，重启无残留。
- 数据目录 `~/Library/Application Support/cc.gouxiang.desktop/`（dev.db/uploads/.audit）与钥匙串项在删 `.app` 后**按 macOS 惯例保留**（符合 Apple 沙盒外应用通行做法）。
- 未来可加（非必须）：应用内"恢复出厂/清除本地数据"、卸载前自检内核已退出、备份轮转。

### 9.2 源码保护分级（由弱到强，按商业节奏选）
现状：后端 `Resources/server/dist/index.js` 为**明文 esbuild JS**（无混淆、无 sourcemap，SQL/路由肉眼可读）；前端明文；仅 Rust 壳是 strip 原生二进制。
1. **L-A JS 混淆/压缩**（terser 混淆、字符串数组化、去注释）：门槛低，挡随手翻阅；几乎不影响构建。
2. **L-B 字节码/v8 snapshot**（如 bytenode 或 Node SEA/单文件可执行）：把 JS 变字节码/编译进二进制；需评估 esbuild 产物、better-sqlite3/prisma 原生模块、启动耗时与可调试性，**必须在 VM 与真机回归 readyz 五探针**。
3. **L-C 核心逻辑下沉 Rust**：把最敏感的规则/授权/签名校验放进已编译的壳（本来就是 strip 二进制），JS 只留编排。工作量最大、保护最强。
4. **L-D 机密与关键规则服务端化**：真正的护城河是"有价值的能力在服务端"，客户端拿走也跑不全（与 §4 威胁模型一致）。
- 建议顺序：授权先行（本设计 L1→L2）→ 商业利益明确后再投 L-A/L-B → 长期靠 L-C/L-D。混淆/字节码都只是"提高门槛"，不应被当成绝对防护。

## 10. 一页纸结论

- **现在（0.2.5-beta）**：只交本设计稿，零代码改动、零风险。
- **下一版（建议 L1）**：以与 `GX_POC3`/`GX_SYNC_SERVER` 完全一致的"默认关闭"纪律，预埋 `license/gate.rs` 纯函数、恒为 bypassed 的 `gx:license_status` 命令、`GX_LICENSE_MODE=off` 配置占位；四门证明零变化。
- **商业化时（L2/L3）**：打开 verify/enforce，上线签名许可→（可选）订阅激活与功能分级；全程 fail-open、不碰用户数据、私钥不落地。
- **源码保护**单列为 §9 路线，按收益分期投入，不与授权绑定。
