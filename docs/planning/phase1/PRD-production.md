## 一、问题陈述

GouXiangDB v0.1.0 已具备完整的单机智能表格能力（30 种字段、公式引擎、七种视图、KB、画布），主链路与鉴权健康。但它当前是一个**「开发环境能跑」的产品，不是「团队能托付数据」的产品**。

团队把它从个人工具升级为团队私有部署的生产系统时，三个层面的问题会立刻暴露：

1. **数据敢不敢放进去**：单表超过 5000 行即触发全表 `findMany` + 内存 hydrate（基线 R1），附件以 dataURL 内嵌记录 JSON（R2），中期百万行目标下必然卡顿甚至内存溢出；SQLite 无备份工具链，误删、磁盘损坏、升级失败都不可恢复。
2. **权限敢不敢放开**：改密后旧 JWT 不失效、分享链接删除后 member 不回收（R4），无审计日志，敏感字段无法对普通成员屏蔽——管理员没有底气给全员开账号。
3. **系统敢不敢升级**：无 CI（R6）、无监控、无部署包、无回滚预案，发布靠本地手工 build，服务宕了靠用户投诉发现。

现在的替代方案是 Excel/网盘/在线表格 SaaS：前者无法协作，后者数据不在自己服务器上，这正是私有化部署的动因。**本期要解决的不是功能缺失，而是「可托付、可运维、可恢复」。**

## 二、目标用户与痛点场景

### 角色 1：内部用户（普通成员，主要用户画像）

- 画像：团队成员 10–50 人，含非技术背景的业务人员；浏览器为主，部分人用桌面端；技术水平参差。
- 典型痛点：
  - P-U1：录入到几千行后列表滚动、筛选明显卡顿，关联多的表打开要等数秒（R1 的直接体感）。
  - P-U2：附件多的表加载慢，一个 2MB 附件内嵌在记录 JSON 里，全表读取时被一起拖进内存（R2）。
  - P-U3：表格误操作后没有撤销手段（grid 无 undo，基线 R5），担心自己改坏数据。
  - P-U4：服务重启或升级时页面白屏/报错，没有任何「系统维护中」提示，不知道该等还是该报障。
  - P-U5：桌面端版本与服务端能力不一致时出现兼容性问题，无更新机制。

### 角色 2：管理员（Base / 工作区管理员，关键决策画像）

- 画像：团队负责人或数据 owner，懂业务不一定懂代码；负责开账号、定权限、管分享。
- 典型痛点：
  - P-A1：权限只有角色级粗粒度，无法对普通成员隐藏「联系方式」「薪酬」等敏感字段；只能拆表，破坏数据关联。
  - P-A2：分享链接发出去后无法真正回收（删除后分享 member 不回收，R4），也不能设有效期/访问密码，对外协场景不敢开分享。
  - P-A3：成员离职、密码泄露后，旧 token 仍有效（JWT 改密不失效，R4），无法一键「踢下线」。
  - P-A4：没有审计记录，出了数据问题查不到谁在什么时候改了什么、谁导出过数据。
  - P-A5：存储用量不透明，附件持续增长，磁盘被写满前没有任何预警。
  - P-A6：无法把整个 base 导出归档或迁移交接，数据被「锁」在系统里。

### 角色 3：运维者（私有化部署负责人，本期新增画像）

- 画像：通常是团队内兼职 IT / 全栈开发，一个人管部署、升级、备份；不一定有专职 DBA。
- 典型痛点：
  - P-O1：**没有备份**。知道 SQLite 是单文件，但直接复制可能拷到 WAL 半写状态；不知道正确的一致性备份姿势，也没恢复过——「备份从未演练 = 没有备份」。
  - P-O2：升级有心理负担。`prisma migrate deploy` 一旦失败或新版本有问题，没有回滚路径，生产数据可能卡在中间态。
  - P-O3：没有部署交付物。当前靠 clone 仓库、手写 `.env`（历史上踩过绝对路径的坑，R8）、手工 build，换机/换服务器无法复现。
  - P-O4：没有监控与告警。健康端点只有 `db:ok` 粗粒度状态，服务挂了、磁盘满了、备份失败了都靠用户反馈才知道。
  - P-O5：没有 CI，发布物来自某个人的本机，环境漂移、漏跑测试全靠自觉。
  - P-O6：HTTPS、密钥、防火墙等加固项没有清单，只能照着网上零散文章做，容易漏。

## 三、竞品 / 对标分析：私有化生产化怎么做

> 行业基线（企业管理/ERP 知识库）：私有化企业产品的核心诉求是流程标准化、权限分级、可审计；反模式是花哨视觉和忽视权限的 UI 表达。以下为 NocoDB / Baserow / SeaTable 三家公开私有化文档的对标结论（2026-09 检索）。

| 维度 | NocoDB | Baserow | SeaTable | 对 GouXiangDB 的启示 |
|------|--------|---------|----------|----------------------|
| 生产数据库 | 官方建议 PostgreSQL（SQLite 仅试用） | PostgreSQL + Redis（横向扩展前提） | MariaDB/MySQL，生产建议独立库 | 三家默认服务端库；我们按 ADR-0002 坚持 SQLite 单实例，但**必须用压测证伪百万行瓶颈**，并保留 dialect 抽象 |
| 备份范式 | 三件套：`pg_dump` + 附件卷 tar + 配置文件；daily cron；明确要求**异地副本**；恢复文档按步骤给全 | `backup_baserow`/`restore_baserow` 管理命令（tar.gz）；强调**停服备份**、恢复到空库不覆盖 | 官方 **restic 备份容器**：加密、去重、多目标（S3/B2/本地）；四件套=DB dump+base 数据+配置+凭据 | 共同范式＝**「数据库一致性快照 + 文件目录 + 配置」+ 定时 + 异地 + 恢复演练**。我们的 SQLite 对应物：在线 `.backup`/`VACUUM INTO` + `uploads/` + `.env` 模板，M2 必须交付 |
| 升级迁移 | 镜像 tag 固定（禁 latest）、systemd 托管、升级前手动快照 | 启动自动迁移，`MIGRATE_ON_STARTUP=false` 可关；大版本先备份 | 小版本直接拉镜像，大版本先备份并在测试环境验证 | 迁移必须**显式可控**（自动但可关）、升级前自动快照、版本 tag 固定 |
| 健康检查 | `/api/v1/health` 明确要求接入监控 | 容器健康检查 | 容器化 + 日志 | 健康端点拆分 liveness/readiness 是低成本标配（M1/M3） |
| 加固清单 | 官方 production hardening checklist：防火墙端口、secret 文件 600 权限、日志轮转（max-size/max-file）、SELinux、出站白名单 | 外部 DB 最小权限、只读账号连外部库 | 独立 DB 容器、强密码、HTTPS | 我们应产出**一份一页纸加固清单**随部署包交付（密钥权限、HTTPS、速率限制、日志轮转） |
| 权限 | 社区版粗粒度 RBAC；字段级/SSO/审计属企业版付费 | RBAC 高级版在付费层 | 企业版才有细粒度权限/审计 | 细粒度权限是商业护城河而非开源标配；本期做到**字段级权限（P1）**即超过开源社区版水平，SSO 不做 |
| 交付形态 | docker-compose 单服务器安装脚本 + 反代/Caddy 集成 | all-in-one 单镜像 或 compose 多服务 | compose + Caddy 自动证书 + 备份容器 | 三家均以容器为主流，但这建立在"客户运维会装 Docker"的前提上。我们的部署操作者可能是非专业运维、客户机能否装 Docker 尚未确认（见外部依赖 1），故裁决为**双轨、裸机优先**：默认交付物＝幂等 `deploy.sh` + systemd 单元 + Caddy 配置 + 一页纸 runbook（不依赖 Docker）；docker-compose 仅作为环境验证通过后的可选交付，不追集群 |
| 差评/痛点（社区反馈） | SQLite 上生产被官方劝退；JWT 密钥不固定会导致全员掉登录 | 外部 PG 备份姿势社区反复踩坑（备份出 90KB 空文件）；CSRF 与域名配置耦合 | 日志表膨胀撑大 dump，需 ignore-table 拆分 | 印证：备份必须**验证可用性**（不能只看文件生成了）；密钥必须固定；日志/审计表要有保留期清理 |

**对标总判断**：我们不需要、也不应该照搬三家的重型架构（PG 集群、Redis、多 worker、S3 依赖）。团队 10–50 人、单实例、百万行铺路的定位下，真正决定「能不能生产用」的是它们共有的轻量实践：**一致性备份三件套 + 恢复演练、健康检查、密钥固定、固定版本发布、加固清单**。这些全部可以在 SQLite 技术栈上以低成本实现，是本期的对标落点。

## 四、我们的差异化

用户为什么选 GouXiangDB 而不是直接私有化部署 NocoDB/Baserow：

1. **零外部依赖的私有化**：默认裸机交付——一条幂等 `deploy.sh` 配好 systemd + Caddy，不需要先装 Docker，更不需要先装/运维 PostgreSQL、Redis、对象存储；兼职运维一个人能管。环境具备 Docker 的客户可选装 compose 包，但 Docker 从不是前提。
2. **备份恢复对 SQLite 场景做到开箱即用**：竞品的备份文档都假设你有 DBA 知识（pg_dump、停服、空库恢复）；我们提供一键脚本 + 调度 + 演练手册，备份成功且**可恢复**双重校验。
3. **超越开源社区版的权限粒度**：字段级可见性（P1）+ 分享链接全生命周期 + 审计日志，而这些在对标产品中多为付费企业版。
4. **画布/KB 一体化**是产品功能层差异，本规划负责让这份差异「敢被团队用起来」。

## 六、里程碑分期（4 个双周迭代，共 8 周）

> 节奏原则：每个里程碑结束都必须是**可发布、可回滚**状态，并跑一遍 40 条历史回归用例（`docs/baseline/2026-09-12-regression-cases.md`），重点看护 R1 数据链路与 R10 画布契约。
>
> **编号对齐**：本章保留 PM 的 M1–M4 叙事编号；架构师文档使用 P0–P3 阶段编号。两套编号的显式映射见本章末「6.1 PM 里程碑 × 架构阶段对照表」，排期与验收以该表为准，禁止再各说各话。

### M1（第 1–2 周）：容量地基 + 质量门 + 部署形态探针

- 目标：让「百万行铺路」从口号变成有数据支撑的工程方向；让每次提交有自动质量门；第一时间消除「客户能不能装 Docker」的交付形态不确定性。
- 交付：E1 CI 质量门（含 R6 清理）、A1 SQL 化分页、A4 慢请求日志、D1 健康端点拆分、A2 百万行压测报告（10 万/50 万/100 万三档）、**E8 Docker 可行性探针（≤1 人日，出结论：目标客户环境普遍可装 / 不可装 / 不可控）**。
- 出口验收：
  - Given 单表 50 万行，When 普通成员打开列表并翻页，Then 首屏与翻页 P95 < 800ms，API 内存不随全表行数线性增长。
  - Given 迁移版本与数据库不一致，When 访问 readiness，Then 返回未就绪且原因可读，liveness 仍正常。
  - Given 向 Gitee 推送 PR，When CI 完成，Then typecheck/单测/构建/冒烟全绿才允许合并。
  - Given 目标客户的典型干净环境，When 执行 Docker 探针，Then 产出书面结论（能否安装、离线镜像是否可达、是否需要 root）；结论为「不可装/不可控」时，E8 的 compose 部分正式取消，全程走 E2 裸机。
- 关键决策点：**A2 报告若证伪 SQLite 路线（百万行 P95 远超目标），主理人 + 架构师立即评审是否提前启动 ADR-0008（切 PG，编号对齐架构 §6），后续里程碑重排。**

### M2（第 3–4 周）：安全加固 + 备份恢复 + 裸机部署包

- 目标：管理员敢开全员账号；运维敢说「数据丢了能找回」；拿到一台**没装 Docker** 的干净 Linux 就能照 runbook 上线（M2 末形成首个「可私有部署版」，对齐架构 P0→P1 之间的发布点）。
- 交付：B1 速率限制、B2 安全头/HTTPS 指引、B3 JWT 治理、B4 分享全生命周期、A3 附件外置（含存量迁移）、**A9 字段约束变更存量校验（R3）**、C1 一键备份、C2 调度与保留、C3 恢复演练（首次实战，产出演练记录）、**E2 裸机部署包（幂等 deploy.sh + systemd 单元 + Caddy 配置 + 一页纸 runbook）、E3 迁移发布管线、D2 结构化日志（随部署包接入 journald，对齐架构 P0）**。
- 出口验收：
  - Given 成员修改密码，When 使用旧 token 请求，Then 收到 401；管理员「踢下线」后该用户全部会话失效。
  - Given 连续 10 次错误登录，When 第 11 次尝试，Then 触发限制并记录审计/日志。
  - Given 一个运行中的实例，When 执行备份并在干净环境恢复，Then 抽样记录、附件、分享配置一致，恢复耗时 ≤ 2h，备份点数据丢失 ≤ 24h（RPO/RTO）。
  - Given 存量附件数据，When 执行 A3 迁移脚本，Then 记录中的附件可正常访问，fields JSON 体积显著下降，迁移可重复执行不产生脏数据。
  - Given 把一个字段改为「唯一/必填」（A9），When 存量数据存在重复/空值，Then 先生成含违反条数与定位的校验报告，管理员选择「拒绝生效」或「迁移后生效」前，新约束不落地、存量不被静默污染。
  - Given 一台未安装 Docker 的干净 Linux 服务器（含离线场景），When 按 runbook 执行 deploy.sh，Then 60 分钟内服务经 HTTPS 可访问、`/api/health/ready` 通过、首个管理员账号完成初始化；重复执行脚本幂等不报错。

### M3（第 5–6 周）：可观测性 + 异地备份加密 + compose 可选交付

- 目标：故障能被主动发现；备份离开本机时是密文；若 M1 探针通过，给偏好容器的客户补 compose 可选包。
- 交付：D3 指标端点、D4 告警、C4 异地副本（**含备份产物 age X25519 收件人静态加密——备份机只放公钥 AGE_RECIPIENT、解密私钥离线另存、runbook 解密步骤**）、C5 升级前快照/回滚、A5 筛选/排序 SQL 下推、**E8 docker-compose 可选包 + 离线镜像 tar（仅当 M1 探针结论为「普遍可装」时交付，否则关闭）**。
- 出口验收：
  - Given 备份任务连续失败或磁盘使用 >85%，When 触发条件，Then 运维在约定渠道收到告警。
  - Given 当前版本运行中，When 执行升级脚本到新版本，Then 升级前自动产生快照；升级失败时一条命令回滚到原版本与数据。
  - Given 备份任务执行，When 产物推送异地，Then 异地留存文件为密文、备份机仅持公钥（无私钥）不可读；runbook 的「取离线私钥→解密→校验→恢复」在干净环境走通一次。
  - Given M1 探针通过，When 客户选择容器形态，Then 用 compose 包在干净环境完成同等部署，功能与裸机形态一致；探针未通过时本条不适用，资源不投入。

### M4（第 7–8 周）：多端发布 + 生产验收

- 目标：多端发布物齐备，以一次正式灾备演练（**走密文异地备份**）和百万行终验宣告生产化就绪。
- 交付：E4 chunk 分包、E5 版本化发布、E6 Tauri 安装包（按证书可得性）、B8 初始化引导（若 M2 容量紧张可顺延至此）、A2 终验复测、全量灾备演练（模拟整台服务器丢失，从密文异地备份恢复）。
- 出口验收：
  - Given 模拟主机完全损毁，When 用异地**密文**备份在新机按 runbook 取离线私钥解密恢复，Then RTO ≤ 2h、RPO ≤ 24h，演练记录归档（含取私钥与解密耗时）。
  - Given 百万行终验数据集，When 跑核心场景（列表/筛选/关联/公式/附件/视图切换），Then 全部达到非功能指标（见第七节）。
  - Given 桌面端用户，When 安装发布包并连接生产服务，Then 核心功能与 Web 一致；版本不兼容时有明确提示而非白屏。

| 备份安全 | 异地备份产物用 **age X25519 公钥收件人模式**静态加密：备份机/cron 只放公钥 AGE_RECIPIENT（泄露无害、仅可加密），解密私钥 identity 永不落生产/备份机、离线另存（密码库/离线介质），恢复时经 AGE_IDENTITY_KEY 临时注入、用后销毁；恢复 runbook 含「取离线私钥→解密」步骤并有演练记录 | P1 |
| 可观测性 | 结构化日志 + 请求 ID；readiness/liveness 分离；关键指标可被 Prometheus 抓取 | P1 |
| 可访问性 | 权限矩阵、后台页面键盘可达、对比度符合 WCAG 2.1 AA 基本要求 | P2 |
| 国际化 | 本期中文为主，错误文案与时间格式预留 i18n 边界 | P2 |
| 图标方案 | 统一 SVG 图标库（由架构师选型锁定），禁止 emoji 图标 | P0（团队规则） |

## 八、数据埋点方案

> 私有部署场景默认数据不出内网；埋点走自建轻量 `trackEvent()` 落本地日志/表，不接外部 SaaS，不采集记录内容等隐私数据。

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 获客/初始化 | `instance_initialized`, `admin_setup_completed` | 部署完成率、初始化向导转化 |
| 激活 | `base_created`, `first_record_created`, `first_share_created` | 团队是否真正用起来 |
| 容量/性能 | `list_page_slow`（>800ms）、`api_error_occurred`、`sqlite_busy_hit` | A2 压测之外的真实容量信号 |
| 留存 | `session_start`, `session_duration` | DAU/使用频次 |
| 安全 | `login_failed`, `rate_limited`, `share_revoked`, `token_revoked` | 与审计日志互补（审计重详情，埋点重聚合） |
| 备份运维 | `backup_completed`, `backup_failed`, `backup_encrypted`, `restore_performed`, `restore_decrypt_failed`, `upgrade_succeeded`, `upgrade_rolled_back` | 验证运维链路真实使用率；解密失败单独可见 |
| 数据完整性 | `field_constraint_scan_started`, `field_constraint_conflicts_found`, `field_constraint_change_rejected`, `field_constraint_migrated` | 度量 A9（R3）存量校验的触发频次与冲突规模，不含字段内容 |
| 异常 | `frontend_error_occurred`（message/stack 摘要、version、device，不含输入内容） | 白屏发现机制 |

实现要求：事件命名 `{对象}_{动作}`；公共属性 `instance_id`（脱敏生成）、`timestamp`、`role`、`version`、`device`；不上报 IP、不同步记录原文。

## 九、关键验收标准（Given/When/Then 摘录）

- Given 未设置 `JWT_SECRET` 等必填环境变量，When 启动 API，Then 进程拒绝启动并打印缺失项，不以默认弱密钥运行。
- Given 分享链接设置了 7 天有效期，When 到期后访问，Then 返回失效页；管理员吊销后，对应分享 member 立即回收，旧链接不可再写。
- Given 备份目标磁盘剩余空间不足，When 到达调度时间，Then 不产生半截备份文件，运维收到失败告警，上次有效备份保留。
- Given 备份文件损坏，When 执行恢复，Then 校验阶段即失败并明确报错，不污染现有数据目录。
- Given 普通成员对某字段无可见权限，When 通过任何接口（列表、详情、导出、公式引用）读取，Then 该字段一律不返回（服务端强制，而非仅前端隐藏）。
- Given 一台未装 Docker 的干净 Linux（含离线环境），When 按 runbook 执行幂等 deploy.sh，Then 60 分钟内服务经 HTTPS 可访问、ready 探针通过、初始化向导可用；重复执行不产生副作用。
- Given 备份产物已推送异地，When 备份机（仅持公钥 AGE_RECIPIENT）尝试打开该文件，Then 内容为 age X25519 密文不可读；在干净环境取用离线私钥 identity 按 runbook 解密后 sha256 校验通过并可正常恢复。
- Given 管理员把某字段改为「唯一」而存量存在重复值，When 提交设置，Then 先返回存量校验报告（违反条数与定位），在管理员显式选择处理策略前新唯一约束不生效，存量数据不被静默改动。
- Given 单表行数超过计算字段置灰阈值，When 用户尝试对 formula/lookup/rollup/count 列排序或筛选，Then 入口置灰并给出改用物理字段的提示，而非触发全表异步计算或长时间白屏。
- Given 服务正在重启，When 用户访问页面，Then 看到维护提示而非连接错误/白屏（M4 前以公告文档兜底）。

## 十、边界条件

| 类型 | 必须覆盖 |
|------|----------|
| 空状态 | 无 base/无表/无记录时运维概览与备份页的引导；备份目录为空时的首次运行 |
| 错误状态 | 备份失败、迁移失败、磁盘满、上传超限/类型不符、鉴权过期、裸机离线依赖缺失、**解密失败（私钥错误/离线私钥丢失）须报错可读、不留半截解密产物、不覆盖现有数据目录** |
| 加载状态 | 大表分页加载、附件迁移进度、**字段约束存量校验扫描进度**、备份/恢复/解密进度（长任务不可让页面假死） |
| 边界值 | 单文件大小上限、附件总量配额、单表百万行、分享密码长度、保留期天数（含 0/负数非法值） |
| 计算字段大表口径（产品裁决） | **采纳架构建议：大表场景对计算字段（formula/lookup/rollup/count）的排序与筛选「禁用并提示」，不做异步全量计算。** 阈值按行数（如单表 >5 万行，具体值随 A2 压测校准）：超阈值时，计算字段列头的排序/筛选入口置灰并提示「该列为计算字段，大表下不支持排序/筛选，请改用物理字段或缩小范围」；物理字段的排序/筛选经旁路索引正常下推，不受影响。计算字段仅对当前页/过滤后结果在应用层求值，不承诺全表 SQL 下推（与架构 §2.3 非目标一致）。表尾聚合（SUM/AVG 等）对计算字段同理：大表下提示统计可能不精确或不提供，物理字段走 SQL 聚合 |
| 字段约束变更（R3） | 改「唯一/必填」或变更 relationKind 前先跑存量扫描；存在违反记录时，用户必须在「拒绝生效（维持旧设置）」与「迁移后生效（去重/补默认值/收敛 linkRow）」间显式选择，不允许静默应用；扫描进行中禁止二次提交；迁移前自动快照（复用 C1/C5） |
| 并发 | 备份进行中发生写入（在线快照必须容忍）；多人同时编辑触发 SQLite BUSY；两个备份任务并发（加锁互斥） |
| 离线 | 无外网环境下安装、运行、恢复/解密全程不依赖许可证回调或外部 CDN（与 NocoDB license 回调模式刻意不同）；加密/解密工具（age，X25519 模式）须纳入离线依赖清单 |
| 权限拒绝 | 越权访问他人 base/隐藏字段/管理接口，一律 403/404 受控返回，不泄漏资源存在性，不出现 500 |
| 升级兼容 | 从 v0.1.0 基线直接升级到 M4 版本的迁移路径必须实测；桌面端连高版本服务端时给兼容提示 |

## 十一、本期 Out of Scope（明确排除）

1. **公有多租户 SaaS**：租户隔离、租户计费、开通流程、公网运营——本期只做团队私有部署。
2. **数据库实际切换 PostgreSQL/MySQL**：仅做 A8 方言边界抽象与 A2 容量验证；真正切换以 A2 证伪为触发条件，另立 ADR-0008（编号对齐架构 §6 ADR 清单，ADR-0003 为私有部署拓扑决策）。
3. **高可用/横向扩展**：主从、多实例、负载均衡、Redis、共享会话、多副本、K8s/容器编排——单实例 + 自动重启 + 备份恢复即本期可用性答案。docker-compose 仅为单服务器可选形态（E8，受 M1 探针开关控制），裸机 systemd 才是默认与承诺交付物。
4. **计算字段（formula/lookup/rollup/count）的 SQL 物化与异步全量计算**：本期不做物化视图/后台全量重算；大表上对计算字段排序/筛选按第十节口径「禁用并提示」，物理字段路径不受影响。
5. **SSO/SAML/OIDC、SCIM、企业目录（AD/LDAP）同步**：保留账号体系现状，B3/B9 先解决安全底线。
6. **实时多人协同编辑（OT/CRDT）**：现有乐观锁/版本控制维持。
7. **行级高级权限、单元格级权限、自定义审批工作流引擎、自动化规则引擎、AI 能力**：字段级权限（B7）是本期权限粒度上限。
8. **移动端原生 App 与应用市场分发**：响应式 Web + Tauri 桌面端。
9. **插件/模板市场、多语言国际化正式支持、S3 对象存储作为强制依赖**（异地备份的 S3 兼容目标仅作为可选输出端）。

## 十二、风险与依赖

### 风险

| 风险 | 等级 | 应对 |
|------|------|------|
| SQLite 扛不住百万行假设被 A2 压测证伪 | 高 | M1 末设硬性决策点；证伪即启动 ADR-0008（切 PG，对齐架构 §6），A8 方言抽象降低切换成本；里程碑允许重排 |
| 附件存量迁移（A3）涉及生产数据搬运 | 中 | 迁移前强制快照（复用 C1）；迁移脚本幂等、先影子校验再切换、可回退；在低峰窗口执行 |
| 备份「显示成功但不可恢复」 | 中 | C3 要求每双周演练；备份产物内置校验信息；恢复在干净环境而非本机覆盖 |
| CI/部署环境差异（团队 Gitee CI 能力、目标服务器是否允许 Docker） | 中 | M1 第一时间验证 Gitee CI runner；**E8 Docker 探针在 M1 出结论，退路明确——目标机不能装 Docker 或结论不可控时，compose 直接取消，全程走 E2 裸机 deploy.sh + systemd（不依赖容器），部署能力不受影响** |
| 离线环境拉不到依赖/镜像 | 中 | 裸机包附离线依赖清单（含 age 加解密工具、Node 运行时、裁剪后 node_modules），M2 出口验收含断网裸机安装；仅当 E8 探针通过，才额外提供 compose 镜像导出 tar（M3） |
| 备份解密私钥丢失导致备份不可解密 | 中 | X25519 模式下公钥可放备份机、解密私钥 identity 永不落生产/备份机，离线另存（密码库/离线介质）；runbook 明确私钥保管责任与双副本建议；C3 演练必须包含「取离线私钥→解密」全链路；私钥错误时报错可读、不覆盖现库 |
| 双周容量被功能升级主线挤占，生产化欠债 | 中 | 生产化 P0 与功能迭代同优先级；每里程碑出口验收不过不进入下一主题 |
| Tauri 签名证书/Apple 公证不可得 | 低 | E6 不阻塞主线上线；先出未签名包 + 安装指引，签名作为 P1 跟进 |
| 审计/日志表自身膨胀（SeaTable 已踩坑） | 低 | 建表即带保留期清理任务，备份脚本支持大表拆分 |

### 外部依赖（需主理人/客户确认）

1. 部署目标环境：服务器 OS（是否统一 Linux + systemd，有无 Windows Server）、CPU/内存/磁盘规格、**是否可装 Docker（由 M1 的 E8 探针实测，不再凭空假设；不可装则走裸机）**、是否允许内网反代与 80/443。
2. 备份异地位置：NAS/SMB 路径或 S3 兼容端点及凭据；age X25519 **解密私钥 identity 的保管责任人与离线存放位置**（密码库/离线 U 盘；公钥 AGE_RECIPIENT 放备份机，无需保密）。
3. 域名与 HTTPS 证书来源（自签/内部 CA/公网证书）。
4. 团队真实规模（人数、并发）与预期数据量，用于校准 A2 压测档位、计算字段大表置灰阈值与告警阈值。
5. 桌面端发布所需签名资质（Apple Developer、Windows 代码签名证书）是否采购。

## 十三、PM 结论（RoleVerdict，v1.1）

- **裁决：GO（有条件）**。产品功能基线健康（无未修复 P0、270 单测全绿），生产化缺口全部是已知工程项、无需求黑盒，可以按双周节奏立即开工；硬决策点两个：M1 末的百万行压测结论（决定数据库路线）、M1 的 Docker 探针结论（决定 compose 是否投入，但不影响裸机承诺）。
- **最高优先级三件事**：① E1 CI 质量门 + A1 SQL 分页 + A2 百万行压测 + E8 Docker 探针（M1，同时消除数据库路线与部署形态两个不确定性）；② C1/C2/C3 备份三件套（含 C4 静态加密口径前置设计）与首次恢复演练 + **E2 裸机部署包/E3 迁移管线**（M2，数据可托付的底线 + 首个可私有部署版）；③ M3 异地密文备份、可观测性告警与（探针通过前提下的）compose 可选包。
- **部署形态（总监裁决）**：双轨、裸机优先——默认且承诺的交付物是幂等 deploy.sh + systemd + Caddy + 一页纸 runbook（P0，M2 与架构 P0 同期）；docker-compose 降为 P1 可选，以 M1 探针结论为开关；客户不能装 Docker 时有确定退路，部署不被容器绑架。
- **本期补齐的两个基线缺口**：A9 字段约束变更的存量校验（R3，P1，随 M2 数据链路改造）；C4 异地备份静态加密 + runbook 解密步骤（P1，M3 落地、M4 密文灾备终验）。
- **产品口径**：计算字段（formula/lookup/rollup/count）在超大表上排序/筛选采纳架构建议——超阈值禁用并提示，不做异步全量计算（第十节已写明阈值与文案），不承诺计算字段 SQL 下推。
- **节奏**：4 个双周 = 8 周，M1–M4 与架构 P0–P3 的映射以第 6.1 对照表为唯一对齐口径；M1 容量地基/质量门/部署探针 → M2 安全、备份与裸机部署包 → M3 可观测性、密文异地备份与可选 compose → M4 多端发布与整机密文灾备演练终验。
- **刻意不做**：多租户、PG 切换、集群/容器编排高可用、计算字段 SQL 物化、SSO、实时协同、行级权限——全部书面排除，防止生产化规划膨胀成平台重建。
